## 1. k6 이 뭔가

부하 테스트 도구다. 자바스크립트로 "요청 하나를 어떻게 보낼지" 만 적으면,
그걸 **동시에 수천 번** 반복해 주고 결과를 통계로 요약해 준다.

알아야 할 용어는 셋뿐이다.

| 용어 | 뜻 |
|---|---|
| **VU** (Virtual User) | 가상 사용자 한 명 = 요청을 보내고 응답을 기다리는 실행 단위 하나. VU 5,000개면 최대 5,000개 요청이 동시에 떠 있을 수 있다 |
| **iteration** | 스크립트의 `export default function` 을 한 번 실행한 것. 여기서는 "쿠폰 발급 요청 1건" |
| **executor** | 부하를 거는 방식. 아래 참고 |

executor 는 크게 두 종류로 나뉘고, 이 차이가 결과 해석에 계속 영향을 준다.

- **열린 모델**(`constant-arrival-rate`): "초당 5,000건씩 보낸다". 앱이 느려도 계속 보내려 하고,
  보낼 여력이 없으면 **그냥 버린다**. 지금 이 프로젝트가 쓰는 방식이다.
- **닫힌 모델**(`shared-iterations` 등): "총 20,000건을 보낸다". 앱이 느리면 오래 걸릴 뿐 버리지 않는다.

이 프로젝트의 시나리오(`scripts/windows/k6/*.js`)는 이렇게 생겼다.

```js
export const options = {
  scenarios: { issue: {
    executor: 'constant-arrival-rate',
    rate: 5000, timeUnit: '1s', duration: '30s',   // 초당 5,000건 × 30초 = 150,000건
    preAllocatedVUs: 2000, maxVUs: 5000,           // VU 는 최대 5,000개까지
  } },
};

export default function () {                        // 이 함수 한 번 = iteration 한 번
  const userId = Math.floor(Math.random() * USER_POOL) + 1;
  const res = http.post(`${BASE_URL}/api/v1/coupons/${COUPON_ID}/issue`, null, {
    headers: { 'X-User-Id': String(userId) },
  });
  check(res, { 'route exists (not 404)': (r) => r.status !== 404 });
}
```

## 2. 왜 Docker 로 쓰나

Windows 에 k6 을 설치하지 않고 `docker-compose.yml` 의 `k6` 서비스로 돌린다.

- 설치 불필요. 이미지 태그를 `2.2.0` 으로 고정해 뒀으니 브랜치를 옮겨도 러너가 동일하다
- k6 컨테이너가 앱과 **같은 도커 네트워크** 안에 있어 `http://coupon-service:8080` 으로 직접 붙는다.
  Windows 의 `localhost:8080` 포트포워딩을 안 거치므로 그쪽이 병목이 되지 않는다
- `profiles: ["load"]` 라서 평소 `docker compose up -d` 에는 뜨지 않는다

## 3. 실행 방법

PowerShell 에서 프로젝트 루트로 이동한 뒤:

```powershell
.\build-and-run.ps1                              # 앱이 내려가 있으면 먼저

.\scripts\windows\load-test.ps1 over_issuance        # 과발급 검증
.\scripts\windows\load-test.ps1 duplicate_issuance   # 중복발급 검증
```

스크립트가 **쿼리 로그 끄기 → 리셋 → 쿠폰 생성 → k6 → 검증** 을 한 번에 한다.
한 사이클에 1분쯤 걸린다.

mac/bash 환경은 `scripts/load/` 에 별도 판본이 있다 (로컬 k6 + jq 필요).

### 구현 전환 — 브랜치가 아니라 이미지 태그로

`naive`(v0 결함 버전)와 `pessimistic`(비관적 락) 등을 **이미지 태그로 나눠 두고** 오간다.
브랜치로 나누면 harness(스크립트·문서)를 고칠 때마다 여러 곳에 포팅해야 하고,
브랜치마다 다른 harness 로 잰 수치는 비교가 성립하지 않는다.

```powershell
.\build-and-run.ps1 -Tag pessimistic     # 빌드 + 기동
.\scripts\windows\load-test.ps1 over_issuance

.\build-and-run.ps1 -Tag naive           # 되돌려서 비교
.\scripts\windows\load-test.ps1 over_issuance
```

선택한 태그는 `.env` 의 `COUPON_IMAGE_TAG` 에 기록되고 compose 가 자동으로 읽는다.
셸 환경변수로 두면 `load-test.ps1` 이 로그 설정 때문에 컨테이너를 재생성할 때
기본 태그로 조용히 되돌아가므로, 파일에 남기는 것이 중요하다.

측정할 때마다 **`측정 대상 이미지: coupon-service:...`** 가 출력되고,
요약 JSON 도 `build/k6/<시나리오>-<태그>.json` 으로 분리돼 결과가 섞이지 않는다.

> 빌드할 때 `-Djib.to.tags` 를 반드시 함께 넘겨야 한다. `build.gradle.kts` 의
> `tags = setOf(project.version.toString())` 가 살아 있으면 새 이미지가 그 태그까지
> 가져가면서 **기존 이미지를 가리키던 태그가 새 것으로 옮겨간다.** 비교 기준을 잃는다.
> `build-and-run` 스크립트가 이미 처리하고 있다.

## 4. 출력 읽는 법

k6 이 마지막에 뱉는 요약에서 **이 여섯 개만** 보면 된다.

```
    checks_total.......: 9401    172.596972/s
    checks_succeeded...: 100.00% 9401 out of 9401
    ✓ route exists (not 404)

    http_req_duration..: avg=21.41s min=35.37ms med=26.25s max=31.33s p(90)=29.74s
    http_req_failed....: 19.66% 1849 out of 9401
    http_reqs..........: 9401   172.596972/s
    dropped_iterations.: 140600 2581.335418/s
    vus................: 110    min=110          max=5000
```

| 지표 | 뜻 | 어떤 값이어야 하나 |
|---|---|---|
| `checks_succeeded` | 우리가 스크립트에 넣은 검사의 통과율 | **100% 여야 한다.** 아니면 경로나 설정이 틀린 것이고 나머지 숫자는 볼 필요 없다 |
| `http_reqs` | 실제로 보낸 요청 수 (와 초당 처리량) | 의도한 150,000 에 가까울수록 좋다 |
| `http_req_failed` | 2xx 가 아닌 응답의 비율 | **이름에 속지 말 것.** 아래 설명 참고 |
| `http_req_duration` | 응답시간. `avg` 평균, `med` 중앙값, `p(90)` 상위 10% 경계 | 낮을수록 좋다. `min` 과 `med` 가 크게 벌어지면 포화됐다는 신호 |
| `dropped_iterations` | **보내려다 못 보내고 버린 요청 수** | 0 이어야 이상적. 크면 의도한 부하가 안 걸린 것 |
| `vus` | 사용된 가상 사용자 수 | `max` 가 설정한 `maxVUs` 에 붙어 있으면 VU 가 모자랐다는 뜻 |

### `http_req_failed` 는 "실패율" 이 아니다

이 지표는 **2xx 가 아닌 모든 응답**을 센다. 그런데 이 서비스에서 409 는 정상 동작이다.

| 상태 코드 | 의미 | 정상인가 |
|---|---|---|
| 200 | 발급 성공 | ✅ |
| 409 `SOLD_OUT` | 재고 소진 → 거절 | ✅ 정상. 재고보다 요청이 많으면 당연히 나온다 |
| 409 `ALREADY_ISSUED` | 이미 받은 사용자 → 거절 | ✅ 정상. 1인 1매 정책이 동작한 것 |
| 404 | 경로가 틀렸다 | ❌ 설정 오류 |
| 500 | 서버 예외 | ❌ 진짜 문제 |

그래서 `http_req_failed 19.66%` 를 보고 "20% 가 실패했다" 고 표에 적으면 오독이다.
404 를 잡으려고 `checks` 를 따로 넣어 둔 이유가 이것이다
(200 을 기대하는 검사를 넣으면 정상적인 409 까지 실패로 잡히므로 쓸 수 없다).

## 5. `dropped_iterations` 는 왜 튜닝으로 안 없어지나

150,000건 중 **140,600건(93.7%)이 버려졌다.** 처음엔 설정 실수처럼 보이지만 아니다.

VU 하나는 요청을 보낸 뒤 **응답이 올 때까지 다음 요청을 못 보낸다.** 그래서:

```
달성 가능한 최대 rate = maxVUs ÷ 응답시간
                     = 5,000 ÷ 22.8초
                     ≈ 219건/초
```

실측 처리량이 172.6건/초였으니 계산과 맞는다. 목표인 5,000건/초를 채우려면
VU 가 `5,000 × 22.8 = 114,000`개 필요하다. 현실적이지 않다.

`WARN: Insufficient VUs, reached 5000 active VUs` 경고가 바로 이 뜻이다.
**k6 이 느린 게 아니라 앱 응답이 느려서 VU 가 전부 대기에 묶인 것이다.**
maxVUs 를 올려도 앱이 그만큼 더 느려질 뿐이라 해결되지 않는다.

`min=35.37ms` 인데 `med=26.25s` 인 것도 같은 이야기다. 포화되기 전 초반 요청은
35ms 로 정상 처리됐고, 26초는 전부 줄서기 시간이다.

## 6. 2026-08-13 측정 분석

`part-2-1-load-test`, `over_issuance` 시나리오 결과.

```
| issued_quantity | total_quantity | issuance_rows | duplicate_users | over_issuance | count_match |
|             756 |           5000 |          7552 |               0 | FAIL          | FAIL        |
```

### 6.1 숫자가 정확히 맞아떨어진다

```
http_reqs 9,401 − http_req_failed 1,849 = 7,552 = issuance_rows
```

성공 응답 수와 실제 INSERT 행 수가 한 건도 안 틀린다. 네트워크 유실이나 삼켜진 예외가
없다는 뜻이라 아래 분석의 전제가 튼튼하다.

### 6.2 `SOLD_OUT` 은 한 번도 안 걸렸다

실패 1,849건이 재고 소진일 것 같지만 아니다. `USER_POOL` 이 20,000명인데 9,401번을
무작위로 뽑으면 같은 사람이 두 번 이상 뽑히는 일이 생긴다. 그 기댓값은:

```
서로 다른 사용자 ≈ 20,000 × (1 − e^(−9401/20000)) = 7,501명
중복으로 뽑힘   ≈ 9,401 − 7,501 = 1,900건
```

| | 계산 | 실측 | 오차 |
|---|---:|---:|---:|
| 성공 (신규 사용자) | 7,501 | 7,552 | +0.7% |
| 실패 (중복 사용자) | 1,900 | 1,849 | −2.7% |

거의 정확히 맞는다. 즉 **실패 1,849건은 전부 `ALREADY_ISSUED` 이고 `SOLD_OUT` 은 0건이다.**

### 6.3 왜 재고 검사가 한 번도 안 걸렸나

`Coupon.isSoldOut()` 은 `issuedQuantity >= totalQuantity` 다. 그런데 카운터가 **756** 에
멈춰 있으니 5,000 근처도 못 갔다. 실제로 7,552장이 나갔는데도 앱은 756장만 나간 줄 안다.

```
동시 트랜잭션이 같은 값을 읽고 각자 +1 해서 덮어씀 (lost update)
   → 7,552번의 증가 중 6,796번 소실 (90.0%)
   → 카운터가 756 에 머묾
   → isSoldOut() 이 true 가 될 기회 자체가 없음
   → 재고 검사가 통째로 무력화 → 사실상 무제한 발급
```

**이는 `scripts/load/README.md` 의 설명과 다르다.** 거기서는 과발급 원인을
"`isSoldOut()` 검사가 race 라 여러 스레드가 같은 재고를 보고 다 통과" 라는
check-then-act 경합으로 설명하는데, 실제로는 그 단계까지 가지도 못했다.
카운터가 망가져서 재고 검사 자체가 무의미해진 것이 관측된 메커니즘이다.

7,552장에서 멈춘 것도 재고 때문이 아니라 **30초가 끝나서**다. 더 돌렸으면 계속 나갔다.

### 6.4 재현성은 좋다

두 번 실행한 결과:

| | 1회차 | 2회차 | 차이 |
|---|---:|---:|---:|
| `http_reqs` | 9,086 | 9,401 | +3.5% |
| `issuance_rows` | 7,266 | 7,552 | +3.9% |
| `issued_quantity` | 727 | 756 | +4.0% |
| **카운터 손실률** | **90.0%** | **90.0%** | **0%** |

부하가 93% 유실되는 와중에도 손실률은 소수점까지 같다.
**정확성 지표는 지금 설정 그대로도 신뢰할 수 있다는 뜻이다.**

## 7. 쿼리 로그 가설 — 세웠다가 기각했다

이 절은 **틀린 가설을 기록해 둔 것**이다. 같은 의심을 다시 하지 않기 위해 남긴다.

### 7.1 가설

`application.yaml` 은 개발 편의를 위해 이렇게 되어 있다.

```yaml
spring.jpa.show-sql: true
logging.level:
  org.hibernate.SQL: DEBUG
  org.hibernate.orm.jdbc.bind: TRACE
```

이러면 쿼리 하나당 로그가 5줄씩 찍힌다 (DEBUG 1줄 + `Hibernate:` 1줄 + 바인딩 파라미터 3줄).

```
Hibernate: select i1_0.id from issuance i1_0 where i1_0.user_id=? and i1_0.coupon_id=? limit ?
binding parameter (1:BIGINT) <- [237]
binding parameter (2:BIGINT) <- [1]
binding parameter (3:INTEGER) <- [1]
```

요청 하나에 SQL 이 4개쯤 나가니 요청당 20줄 이상이다. `System.out` 은 동기화된 스트림이라
한 번에 하나씩만 쓸 수 있으니, 수천 개 스레드가 여기서 줄을 서느라 응답이 21초까지
늘어난 것 아닌가 — 이것이 가설이었다.

### 7.2 실험

`docker-compose.loadtest.yml` 로 로그를 끄고 같은 시나리오를 돌렸다.

| | 로그 ON | 로그 OFF |
|---|---:|---:|
| **앱에 실제 도달한 요청** | 9,401 | 8,691 |
| 발급 성공 | 7,552 | 7,080 |
| 도달 요청의 응답시간 avg | 21.41s | 20.85s |
| 연결 실패 (status 0) | 0 | 16,703 |

### 7.3 결론: 가설 기각

**로그를 꺼도 앱 처리량은 달라지지 않았다.** 도달 요청 9,401 → 8,691,
응답시간 21.41초 → 20.85초. 실행 간 편차(±4%) 안이다.

응답시간 21초는 로그 때문이 아니었다. 진짜 원인은 8절에 있다.

### 7.4 그래도 로그는 꺼 두기로 했다

성능 때문이 아니라 다른 이유로 유지한다.

- 부하 한 번에 로그가 수백만 줄 쌓인다. `docker compose logs` 가 사실상 못 쓰게 된다
- 측정에서 변수 하나를 줄여 둔다

`load-test.ps1` 이 자동으로 적용하고 `docker inspect` 로 **실제 반영됐는지 확인한 뒤**
진행한다. 안 되어 있으면 측정하지 않고 멈춘다.
디버깅 목적으로 로그를 켜고 돌리려면 `-KeepLogging` 을 준다.

Spring 프로파일(`application-loadtest.yaml`) 대신 환경변수를 쓴 이유가 있다.
프로파일 파일은 이미지에 구워지므로 고칠 때마다 재빌드해야 하고, 재빌드를 잊으면
"프로파일은 활성인데 설정은 안 먹은" 상태가 된다. 로그는 계속 찍히는데 겉보기엔
정상이라 **조용히 틀린 측정**을 하게 된다. 환경변수는 컨테이너에서 직접 확인할 수 있어
그 함정이 없다.

## 8. 진짜 병목 — 요청의 66% 가 앱에 닿지도 못한다

로그를 끈 뒤 이상한 수치가 나왔다. `http_req_duration` 의 **중앙값이 0초**인데
성공한 요청만 보면(`{expected_response:true}`) 중앙값이 24초였다.

`data_received` 로 계산해 보면 명확하다. 총 2,311,626 바이트 중 성공 7,020건이
약 266바이트씩 = 1.87MB 를 쓰고 나면, 실패 20,049건에 남는 것은 **건당 22바이트**다.
409 응답은 ProblemDetail JSON 이라 200바이트가 넘는다. 즉 **HTTP 응답을 받은 게 아니다.**

확인을 위해 시나리오에 검사를 추가했다.

```js
check(res, {
  'route exists (not 404)': (r) => r.status !== 404,
  'connected (not status 0)': (r) => r.status !== 0,   // 추가
});
```

결과:

```
✗ connected (not status 0)
  ↳  34% — ✓ 8691 / ✗ 16703
```

**요청의 66% 가 TCP 단에서 튕겼다.** 앱이 느려서 늦게 응답한 게 아니라, 아예 연결조차
받아주지 못한 것이다. 초당 5,000건을 던지는데 앱이 소화할 수 있는 건 300건 남짓이니
연결 수락 큐가 넘친다.

### 8.1 왜 300건/초 인가

앱이 30초 동안 실제로 처리한 요청은 8,691건, 초당 약 290건이다. 로그를 켜든 끄든 같다.

원인은 **모든 요청이 같은 행 하나를 건드린다**는 데 있다.
선착순 쿠폰이므로 `coupon` 테이블의 `id=1` 행 하나에 발급 요청이 전부 몰린다.
InnoDB 는 그 행의 `UPDATE` 를 직렬화하므로, 아무리 많은 스레드가 붙어도
이 한 줄을 통과하는 속도가 전체 처리량의 상한이 된다.

**그리고 이 상한이야말로 세 브랜치가 바꾸려는 대상이다.**
`part-2-2-pessimistic-lock` 은 락을 명시적으로 잡아 정확성을 얻는 대신 이 값이 더 떨어질 것이고,
`part-2-3-redis-lua` 는 경합을 DB 밖으로 빼서 이 값을 크게 올리는 것이 목적이다.
따라서 **처리량(초당 처리 건수)이 6.3 절 표의 핵심 지표**가 된다.

### 8.2 `status 0` 검사가 없었다면

처음에는 `status !== 404` 검사만 있었다. 그런데 연결 실패 시 k6 의 `res.status` 는 **0** 이고,
`0 !== 404` 는 참이라 **검사를 통과한다.** 그래서 요청의 66% 가 앱에 닿지도 않았는데
`checks 100%` 가 떠 있었다.

부하 테스트에서 검사를 넣을 때는 "무엇이 잘못될 수 있는가" 를 다 적어야지,
한 가지만 막으면 나머지가 조용히 통과한다는 교훈이다.

## 9. 무엇을 믿고 무엇을 못 믿나

| 지표 | 신뢰 | 이유 |
|---|---|---|
| `over_issuance` FAIL (7,552 > 5,000) | ✅ | DB 에 남은 사실. 세 번 실행에서 모두 재현 |
| `count_match` FAIL (756 vs 7,552) | ✅ | 위와 같음 |
| 카운터 손실률 90.0% | ✅ | 실행마다 소수점까지 동일. 가장 선명한 정확성 지표 |
| 앱 처리량 약 290건/초 | ✅ | 로그 ON/OFF 양쪽에서 같게 나옴. **브랜치 비교의 핵심 지표** |
| `http_req_duration` 전체 avg | ❌ | 연결 실패(0초)가 섞여 있어 평균이 무의미. `{expected_response:true}` 쪽을 봐야 한다 |
| `http_reqs`, `dropped_iterations` | ⚠️ | **조건부.** 아래 참고 |

### `http_reqs` / `dropped_iterations` 를 언제 믿을 수 있나

2026-08-13 측정에서는 못 믿었다. 요청의 93.7% 가 버려지고 66% 가 TCP 단에서 튕기던 상태라
"보낸 요청 수" 가 앱이 받은 부하와 아무 상관이 없었기 때문이다.

12절 이후로는 사정이 다르다. 부하 전달률(`iterations ÷ 의도한 150,000`)이 94~98% 까지 올라와
`http_reqs` 는 실제로 던진 양을 반영한다. **판단 기준은 이렇다.**

- `dropped_iterations` 가 의도한 요청 수의 10% 이하이고 `vus_max` 가 설정한 상한(5,000)에
  붙어 있지 않으면 → 부하가 계획대로 전달된 것이고 두 지표를 읽어도 된다
- 둘 중 하나라도 어긋나면 → VU 가 대기에 묶여 부하가 안 걸린 것이니 예전처럼 읽지 않는다

`vus_max` 가 상한에 붙어 있는지를 같이 봐야 한다. 그것 하나가 "k6 이 못 보낸 것" 과
"앱이 못 받은 것" 을 가른다.

## 10. 비관적 락 적용 결과 (2026-08-13)

`CouponRepository` 에 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 조회를 추가하고
`CouponService.issue` 가 그것을 쓰도록 바꾼 버전(`coupon-service:pessimistic`)의 측정.

```kotlin
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("Select c from Coupon c where c.id = :id")
fun findByIdForUpdate(@Param("id") id: Long): Coupon?
```

### 10.1 정확성 — 완전히 해결됐다

```
| issued_quantity | total_quantity | issuance_rows | duplicate_users | over_issuance | count_match |
|            5000 |           5000 |          5000 |               0 | OK            | OK          |
```

**정확히 5,000장.** 4,999 도 5,001 도 아니다. 두 결함이 동시에 사라졌다.

- 과발급 없음: `SELECT ... FOR UPDATE` 가 읽기 시점부터 락을 잡으므로
  같은 재고를 두 트랜잭션이 동시에 보고 통과하는 일이 없다
- 카운터 일치: 읽기-수정-쓰기 전체가 락 안에서 직렬화되어 lost update 가 생기지 않는다

검산도 맞는다.

```
http_reqs 27,100 − http_req_failed 22,100 = 5,000 성공 = issuance_rows 5,000
앱 도달 7,886 = 성공 5,000 + 409 거절 2,886
```

### 10.2 비용 — 거의 없다

| | naive | pessimistic | 차이 |
|---|---:|---:|---|
| `over_issuance` / `count_match` | FAIL / FAIL | **OK / OK** | 해결 |
| 앱에 도달한 요청 | 8,691 | 7,886 | −9% |
| 도달 요청의 응답시간 avg | 20.85s | 21.55s | +3% |
| 연결 거부 (status 0) | 16,703 | 19,214 | — |

정확성을 얻으면서 처리량은 사실상 그대로다. 실행 간 편차(±4%)와 구분되지 않는 수준이다.

**이미 그 비용을 내고 있었기 때문이다.** 8절에서 확인한 290건/초 상한은 모든 요청이
`coupon` 단일 행의 `UPDATE` 락에서 직렬화되기 때문에 생긴 것이었다. 비관적 락은
그 직렬화를 `SELECT` 시점으로 **앞당길 뿐** 없던 경합을 새로 만들지 않는다.
그래서 정확성만 얻고 대가는 거의 치르지 않았다.

### 10.3 `connection refused` 의 정체 확인

8절에서는 `data_received` 계산으로 "TCP 단에서 튕긴다" 고 추론했는데,
이번 실행에서 k6 이 에러를 직접 출력해 확인됐다.

```
dial tcp 172.21.0.3:8080: connect: connection refused
```

초당 5,000건을 던지는데 앱이 300건 남짓만 소화하니 연결 수락 큐가 넘쳐
커널이 RST 로 거절하는 것이다. 추론이 맞았다.

### 10.4 다음 단계에 영향을 주는 관찰

`findByIdForUpdate` 는 `isSoldOut()` 검사보다 **먼저** 실행된다.
즉 **재고가 다 떨어진 뒤에 오는 요청도 행 락을 잡으려고 줄을 선다.**
409 로 거절된 2,886건이 전부 그 줄을 통과한 것이다.

`part-2-3-redis-lua` 는 매진 여부를 DB 밖에서 판단해 락 근처에 가지 않고 즉시 거절할 수 있다.
**처리량 차이가 크게 벌어질 지점**이므로 비교할 때 여기를 본다.

### 10.5 이 결과의 신뢰 범위

- **정확성 결론(OK/OK)은 견고하다.** DB 에 남은 사실이고 5,000/5,000/5,000 으로 명확하다.
  naive 가 같은 부하에서 실패했으므로 부하가 부족했던 것도 아니다
- **처리량 수치는 여전히 제한적이다.** 요청의 71% 가 앱에 도달하지 못했다.
  "앱에 도달한 요청 수" 를 대리 지표로 비교했을 뿐이며,
  정밀한 처리량 비교는 부하 모델을 바꾼 뒤에 해야 한다 (11절)

## 11. 남은 과제

- **부하 모델 교체 (우선순위 높음)**: 12절에서 앱 처리량이 14배가 된 뒤에도
  요청의 15% 안팎이 TCP 단에서 튕긴다. 열린 모델로 5,000rps 를 던지는 한
  앱을 아무리 빠르게 해도 accept 큐는 넘치므로, 여기서부터는 부하 모델을 바꾸지 않으면
  더 개선해도 그 효과가 연결 거부에 묻힌다.

  ```js
  scenarios: { issue: {
    executor: 'shared-iterations',
    vus: 200,            // 동시성 — 경합을 일으키기엔 충분하고 연결 폭주는 없음
    iterations: 20000,   // 총 요청 수를 고정 → 구현마다 같은 양이 전달된다
    maxDuration: '5m',
  } },
  ```

  "20,000건을 몇 초에 처리했나" 를 구현끼리 직접 비교할 수 있게 된다.
  `scripts/load/` 의 mac 판본과 부하 조건이 갈리므로 양쪽에 같이 반영해야 한다
- **Tomcat 스레드 가설 검증**: 12.7.6 참고. `server.tomcat.threads.max` 기본값 200 이
  지금 상한인지 확인한다. 다만 위 부하 모델 교체를 먼저 하는 것이 순서다
- **`scripts/load/README.md` 의 과발급 원인 서술 수정**: 6.3 절 내용 반영
- **`scripts/load/` 와 `scripts/api.sh` 의 경로**: `/api/coupons` 로 되어 있으나
  실제 컨트롤러는 `/api/v1/coupons` 라 그대로 돌리면 전부 404 다.
  Windows 판본에만 반영되어 있다

## 12. Redis Lua 개선 — 병목을 따라간 기록 (2026-08-14)

`redis-lua` 구현이 **정확성은 잡았는데 처리량은 pessimistic 과 차이가 없었다.**
원인을 찾기 위해 한 번에 고치지 않고 세 단계로 나눠, 단계마다 이미지 태그를 따로 두고 측정했다.

| 태그 | 무엇을 바꿨나 |
|---|---|
| `lua` | Redis Lua 원자 차감 + 원자 UPDATE (출발점) |
| `lua-fix` | 재고 복구(보상) 로직만 추가. 구조는 그대로 — **대조군** |
| `lua-gate` | Lua 게이트를 DB 접근보다 **앞으로** 이동 |
| `lua-wb` | `coupon` 단일 행 UPDATE 제거, 카운터는 write-behind |
| `lua-pool` | Hikari 커넥션 풀 10 → 50 (코드 변경 없음, 12.7 절) |

### 12.1 결과

`over_issuance` (재고 5,000 / 사용자 20,000 / 5,000rps × 30s):

| | naive | pessimistic | lua | lua-fix | lua-gate | lua-wb | **lua-pool** |
|---|---:|---:|---:|---:|---:|---:|---:|
| 정확성 | FAIL | OK | OK | OK | OK | OK | **OK** |
| 앱 도달 요청 | 8,691 | 7,886 | 8,553 | 8,327 | 7,570 | 80,998 | **120,132** |
| 처리량 (건/초) | ~290 | ~263 | ~285 | ~278 | ~252 | ~2,700 | **~4,004** |
| 성공 응답 avg | 20.85s | 21.55s | 19.12s | 19.76s | 23.31s | 4.44s | **1.32s** |

`duplicate_issuance` (사용자 1,000 / 같은 부하):

| | lua | lua-fix | lua-gate | **lua-wb** |
|---|---:|---:|---:|---:|
| 앱 도달 요청 | — | 91,947 | 84,303 | **113,837** |
| 성공 응답 avg | — | — | 6.18s | **1.67s** |
| 발급 행 수 | 1,000 | 1,000 | 1,000 | **1,000** |

**모든 단계에서 `over_issuance` / `count_match` 는 OK 를 유지했다.** 정확성을 내주고 얻은 속도가 아니다.

### 12.2 `lua` 에는 검증이 못 잡는 결함이 있었다 (과소발급)

`tryIssue` 가 Redis 재고를 DECR 한 뒤 DB 트랜잭션이 롤백되면 **재고가 복구되지 않는다.**
`issuance` 의 `uk_issuance_user_coupon` 위반이 실제 발생 경로다.

`duplicate_issuance` 실행 후 Redis 에 남은 재고를 직접 확인했다 (발급 1,000장이므로 4,000 이어야 한다).

| | 남은 재고 | 누수 |
|---|---:|---:|
| `lua` | 3,977 | **23장** |
| `lua-fix` 이후 | 4,000 | 0 |

23장이 아무에게도 가지 않은 채 사라졌다. **그런데 `verify.ps1` 은 OK / OK / PASS 를 출력했다.**
카운터도 발급 행 수도 롤백과 함께 되돌아가서 DB 안에서는 아무 모순이 없기 때문이다.
DB만 보는 검증으로는 Redis 와 DB 사이에서 새는 것을 잡을 수 없다는 뜻이다.

### 12.3 게이트를 앞으로 옮긴 것만으로는 아무 이득이 없었다

`lua-gate` 는 거절되는 요청이 DB 커넥션조차 잡지 않게 만들었는데도 처리량이 오르지 않았다
(오히려 8~9% 낮다. 실행 간 편차 ±4% 를 감안해도 이득은 확실히 없다).

이유는 **거절 경로가 병목이 아니었기 때문**이다. `lua-fix` 의 `duplicate_issuance` 를 보면
거절 요청은 `SELECT` 2번을 치고도 초당 3,000건 넘게 소화하고 있었다. DB 접근 자체는 싸다.

진짜 제약은 **스레드 고갈**이었다. 게이트를 통과한 5,000건이 `coupon` 행 락에서 각각 20초씩
Tomcat 스레드를 붙들고 있으면, 뒤이어 오는 값싼 거절 요청에 내줄 스레드가 남지 않는다.
게이트를 앞으로 옮겨도 거절 요청이 스레드를 못 얻으면 소용이 없다.

### 12.4 병목은 `coupon` 단일 행 UPDATE 하나였다

`lua-wb` 에서 그 UPDATE 를 핫패스에서 빼자 처리량이 **252 → 2,700건/초, 약 10배**가 되었고
성공 응답시간은 23.31초에서 4.44초로 떨어졌다. 남은 DB 쓰기는 `issuance` INSERT 뿐인데
행마다 달라 서로 직렬화되지 않는다.

8절에서 추정한 "290건/초 상한은 `coupon` 단일 행 경합에서 온다" 가 이것으로 확인됐다.
**비관적 락이든 Redis Lua 든, 그 UPDATE 가 핫패스에 남아 있는 한 처리량은 바뀌지 않는다.**
10.2 의 "비관적 락의 비용이 거의 없다" 도 같은 이야기였다 — 둘 다 같은 벽에 막혀 있었을 뿐이다.

`coupon.issued_quantity` 는 지우지 않고 `IssuedQuantitySynchronizer` 가 1초마다
`total_quantity − (Redis 재고)` 로 덮어쓴다. 그래서 `count_match` 의 의미가 바뀌었다 —
이제 **"Redis 가 센 발급 수" 와 "DB 에 실제로 들어간 행 수" 의 교차 검증**이다.
(`COUNT(*)` 로 채웠다면 언제나 일치해 아무것도 못 잡는 검증이 됐을 것이다.)

### 12.5 그래서 Lua 를 쓰는 의미는 무엇이었나

정합성만 놓고 보면 Lua 는 비관적 락 대비 얻는 것이 없다. 둘 다 5,000/5,000/5,000 을 만든다.
**Lua 의 값어치는 경합 지점을 DB 밖으로 빼낼 수 있다는 데 있고, 그건 DB 쪽 경합을
같이 없앴을 때만 실현된다.** `lua` → `lua-gate` 까지는 Redis 를 붙여 놓고도
DB 경합을 그대로 두었기 때문에 복잡도만 늘고 이득이 없었다.

Lua 스크립트 자체의 역할도 이번에 분명해졌다. `SISMEMBER → GET → DECR → SADD` 네 연산이
한 덩어리로 원자적이어야 하므로 Lua 가 필요하다. 명령이 하나뿐이라면(`DECR`) Redis 가 이미
원자적이라 Lua 를 쓸 이유가 없다.

### 12.6 남은 한계

- 여전히 요청의 21~27% 가 `status 0` 으로 튕긴다. 열린 모델로 5,000rps 를 던지는 한
  앱이 빨라져도 연결 수락 큐는 넘친다. 11절의 닫힌 모델 전환은 그대로 남아 있다
- `lua-wb` 의 처리량 2,700건/초가 새로운 상한인지, 아니면 열린 모델 때문에 그렇게 보이는 것인지는
  아직 모른다. 다음 용의자는 Hikari 풀 기본값 10개와 Tomcat 스레드 200개다
  → **풀 쪽은 12.7 에서 확인됐다.** 스레드는 아직 남아 있다
- 재고의 진실이 Redis 로 옮겨갔으므로 **Redis 를 잃으면 재고 상태를 잃는다.**
  AOF 를 켜 두었지만 이 프로젝트는 복구 절차를 갖고 있지 않다
- 애플리케이션이 `tryIssue` 와 DB 쓰기 사이에서 죽으면 그 한 장은 여전히 샌다.
  보상 로직은 예외만 처리하지 프로세스 중단은 처리하지 못한다

### 12.7 커넥션 풀 — 성공 요청만 느렸던 이유

#### 12.7.1 어디서 출발했나

`lua-wb` 의 출력에서 응답시간이 둘로 갈려 있었다.

```
http_req_duration.............: med=553.59µs        ← 거절 요청 (대부분)
  { expected_response:true }..: avg=4.45s           ← 발급 성공 5,000건만
```

거절은 마이크로초인데 성공만 4.45초다. 발급 자격 판정은 Redis 가 끝내므로
게이트 통과 5,000건은 첫 1초 안에 다 쏟아진다. 그 뒤 DB 쓰기에서 줄을 선다는 뜻인데,
`application.yaml` 에 풀 크기 지정이 없어 **Hikari 기본값 10개**가 쓰이고 있었다.

```
5,000건 ÷ 커넥션 10개 × INSERT 약 9ms ≈ 4.5초        (관측 4.45초)
```

#### 12.7.2 재기 전에 적용 여부부터 확인했다

`maximum-pool-size: 50` 으로 올린 뒤, 수치를 읽기 전에 MySQL 쪽에서 확인했다.

```powershell
docker compose exec -T -e MYSQL_PWD=coupon mysql mysql -ucoupon `
  -e "SHOW GLOBAL STATUS LIKE 'Max_used_connections'"
#   Max_used_connections    51      ← 풀 50 + 방금 친 조회 세션 1
```

지금까지 11 이던 값이 51 로 뛰었다. 7.4 절과 같은 이유다 —
**설정이 안 먹은 채로 재는 것이 이 프로젝트에서 반복된 실패 모드다.**

#### 12.7.3 결과

`over_issuance`:

| | lua-wb (풀 10) | **lua-pool (풀 50)** |
|---|---:|---:|
| 성공 응답 avg | 4.45s | **1.32s** |
| 앱 도달 요청 | 79,576 | **120,132** |
| 처리량 | ~2,653/s | **~4,004/s** |
| `dropped_iterations` | 40,697 | **8,978** |
| 부하 전달률 | 73% | **94%** |
| 연결 거부 (status 0) | 27.2% | **14.8%** |
| `vus_max` | 5,000 (상한에 붙음) | **4,487** |
| 정확성 | OK / OK | **OK / OK** |

`duplicate_issuance`:

| | lua-wb | **lua-pool** |
|---|---:|---:|
| 성공 응답 avg | 1.67s | **0.95s** |
| 앱 도달 요청 | 113,837 | **126,720** |
| `dropped_iterations` | ~6,300 | **2,768** |
| `vus_max` | 5,000 | **2,772** |
| 발급 / Redis 잔여 재고 | 1,000 / 4,000 | **1,000 / 4,000** |

정확성은 두 시나리오 모두 유지됐고 Redis 재고 누수도 없다.

> 이 표의 `lua-wb` 열은 **재현 실행** 값이다. 12.1 표의 `lua-wb` 는 첫 실행(도달 80,998 / avg 4.44s)이고
> 여기는 두 번째 실행(79,576 / 4.45s)이다. 차이 1.8% 로 실행 간 편차 안이라 결론은 같지만,
> 표끼리 숫자가 안 맞아 보이는 이유가 이것이다.

#### 12.7.4 가설은 맞았지만 선형은 아니다

예측은 4.45 ÷ 5 = **0.89초**였는데 실측은 **1.32초**다. 커넥션을 5배로 늘렸는데 3.4배만 빨라졌다.

모든 대기를 커넥션 대기로 몰아 역산하면:

```
풀 10:  4.45s × 10 ÷ 5,000 =  8.9ms/건
풀 50:  1.32s × 50 ÷ 5,000 = 13.2ms/건      건당 48% 느려졌다
```

> 이 계산은 accept 큐 대기와 Tomcat 스레드 대기까지 커넥션 대기로 뭉뚱그린 **근사**다.
> 실제 INSERT 시간이 그만큼 늘었다는 뜻이 아니라, 동시 쓰기를 늘릴수록 건당 효율이
> 떨어진다는 방향만 읽어야 한다.

원인 후보는 여럿이고 이번 측정으로는 어느 것인지 가리지 못했다 —
`issuance` 의 auto-increment 락, 유니크 인덱스 페이지 경합, 커밋마다의 redo 플러시,
그리고 k6·앱·MySQL·Redis 가 한 머신에서 CPU 를 나눠 쓰는 것.

#### 12.7.5 더 큰 성과는 부하 전달률이다

응답시간보다 이쪽이 중요하다.

```
lua-wb   : 109,304 전달 + 40,697 버림 → 의도한 150,000 중 73%
lua-pool : 141,023 전달 +  8,978 버림 → 94%   (duplicate 는 98%)
```

**`vus_max` 가 처음으로 상한(5,000)에 붙지 않았다** — over 4,487, duplicate 2,772.
5절에서 "VU 가 전부 대기에 묶여 의도한 부하의 6% 만 전달된다" 고 했던 상태에서 벗어났다.
9절의 `http_reqs` / `dropped_iterations` 신뢰 조건을 이제 만족한다.

#### 12.7.6 다음 용의자: Tomcat 스레드 200개

**아직 가설이다.** 발급 성공 5,000건이 첫 1.3초에 몰리는데 Tomcat 워커는 기본 200개뿐이라,
나머지가 accept 큐에서 기다리다 14.8% 가 튕기는 그림으로 보인다.
`server.tomcat.threads.max` 를 올려 재면 확인된다.

다만 지금 상태에서는 **닫힌 모델 전환(11절)이 먼저다.** 열린 모델로 5,000rps 를 계속 던지는 한
앱을 아무리 빠르게 해도 accept 큐는 넘치고, 그러면 스레드를 올린 효과도 연결 거부에 묻힌다.
