# 03. 발급 기록 — Kafka 워커와 DLT

**맡는 일:** 접수된 발급을 **나중에** DB 에 쓴다. 사용자는 이미 200 을 받고 떠났다.

![발급 기록의 비동기 쓰기 경로](../diagrams/write-path.svg)

- 토픽 `issuance.requested` 는 파티션 3, 키는 `userId`. **파티션 수가 소비 병렬도의 상한**이고, 같은 사용자의 요청은 순서가 지켜진다.
- **UNIQUE 위반은 삼킨다.** 재처리의 정상 결과인데 예외를 밖으로 뱉으면 워커가 같은 메시지를 영원히 다시 먹는다.
- 1초 × 3회 재시도 뒤 **DLT** 로 간다. DLT 는 로그 테이블에 `PENDING` 으로 쌓이고, 관리자가 골라서 다시 발행한다(한 번에 100건까지).
- **DLT 로 가도 Redis 재고는 되돌리지 않는다.** 이유는 [02](02-issue.md) 의 "발행 실패" 와 같다.
- ⚠ 워커 트랜잭션에 **`coupon` 단일 행 UPDATE 가 되돌아와 있다.** 아래 "남은 과제" 참고.

## 무엇을 했나

### 컨슈머를 3배로 늘렸는데 쓰기가 안 빨라졌다

- **문제.** 쓰기를 큐 뒤로 뺀 뒤 워커의 쓰기 속도는 폴링 틱당 ~155건. 컨슈머를 3배로 늘려도 **157** 이었다.
- **시도.** "한 파티션에 쏠려서 실질 병렬도가 1이었다" 부터 배제했다 — 브로커에서 파티션별 오프셋을 직접 세어 33%씩 고르게 갈렸음을 확인.
  그 다음 원인을 찾았다: [02](02-issue.md) 에서 요청 경로에서 뺀 **그 단일 행 UPDATE 가 워커 안에 다시 들어와 있었다.** 컨슈머 셋이 같은 행 락에 줄을 섰다.
- **결과.** `kafka-nocount` 에서 그 한 줄만 빼자 부하 종료 후 밀려 있던 쓰기(드레인)가 **통째로 사라졌다.** 병목 확정.
- **배운 것.** 큐는 병목을 없애지 않고 응답 밖으로 옮긴다. 경합 지점은 옮겨도 없어지지 않는다.

### 소비 실패 — DLT 는 격리이지 복구가 아니다

- **문제.** 워커 INSERT 가 실패해도 사용자는 이미 200 을 받았다. DLT 로 치워 두면 파이프라인은 안 막히지만, **그 메시지가 남긴 상태(깎인 재고, 막힌 사용자)는 그대로**다.
- **시도.** `issuance` 테이블만 잠깐 rename 해서 소비 실패를 냈다 — MySQL 을 통째로 세우면 요청이 컨슈머까지 오지도 못하므로, **고장을 내되 검증하려는 경로는 살려 두는 것**이 요령이었다.
  당시 보상은 **먼저 DLT 에 보존하고 그 다음 되돌리는** 순서로 붙였다 — DLT 발행이 실패하면 예외가 나가 오프셋이 안 올라가고 재처리되므로 메시지를 잃지 않는다.
  보상을 걷어낸 뒤에는 DLT 를 로그 테이블에 쌓고 관리자가 골라서 재발행하는 경로를 붙였다. 재발행은 이미 깎인 재고로 그 발급을 마저 기록하는 것이라 재고를 다시 깎지 않는다.
- **결과.** 재현 확인. 그리고 **재시도가 파티션을 세운다는 것**이 실측으로 잡혔다 — 같은 파티션의 실패 건 두 번째는 첫 번째의 재시도 3초가 끝난 뒤에야 시작했다(head-of-line blocking).

### Kafka 로 바꿔서 얻은 것

응답시간도 쓰기 처리량도 인메모리 큐와 사실상 같았다. **얻은 것은 성능이 아니라 내구성과 실패 격리(DLT)** 다.
대신 위험의 방향이 뒤집혔다 — 인메모리 큐는 재시작하면 **유실**, 브로커는 남아서 다음 라운드에 **오염**. 같은 "재시작 금지" 인데 이유가 정반대라 측정 하네스의 주의 문구도 다시 썼다.

## 틀렸던 것

- **선언했는데 안 돌던 설정.** 토픽 설정 빈을 만들었는데 토픽이 하나도 안 만들어지고 있었다. 라이브러리를 직접 넣어 **스타터의 자동설정(`KafkaAdmin`)이 빠져** 있었고, 브로커 auto-create 가 가려 줘서 겉으로는 멀쩡했다. 파티션 3도 내 설정이 아니라 브로커 기본값이었고, DLT 토픽은 아예 없었다. 브로커에 토픽 목록을 직접 물어봐서 알았다.
- **같은 결함을 한쪽만 고쳤다.** 발행 실패에 보상을 붙이고 끝냈는데 소비 실패에도 같은 결함이 있었다. 정책이 코드 두 곳에 흩어져 있었던 탓이라 한 클래스로 모았다.
- **정상 동작을 실패로 읽을 뻔했다.** 보상 로그를 한글로 검색했는데 안 나왔다 — 코드가 아니라 콘솔 인코딩 문제였다. 검증 도구도 검증 대상이다.

## 남은 과제

- **`coupon` 단일 행 UPDATE 가 되돌아왔다.** dlt-replay 작업에서 멱등 검사를 넣으며 딸려 들어왔다. 뺄 근거는 여전히 유효하지만 다시 빼면 앱 동작이 바뀌어 새 태그와 재측정이 필요하다. **`kafka-nocount` 이후의 응답시간·효율 기록은 이 UPDATE 가 없다는 전제로 쓰였다.**
- **비블로킹 재시도(`@RetryableTopic`).** 실패 한 건이 파티션 뒤의 정상 건까지 밀어내는 것을 막으려면 재시도를 다른 토픽으로 넘겨야 한다.
- **쓰기 처리량의 상한을 모른다.** `kafka-nocount` 는 쓰기가 부하 구간 안에 끝나서 드레인 폴링에 표본이 안 잡힌다 — "≥160/s, 상한 미상". 억지 숫자를 만들지 않고 "모른다" 로 닫았다. 다시 열면 하네스가 `written_at` 계측 컬럼을 추가한다.
- **`kafka-nocount` 에서 응답 p99 가 6.45 → 11.74ms 로 밀린 이유**를 아직 안 갈랐다. 쓰기가 부하 구간 안으로 들어와 요청 경로와 무엇을 다투는지(Hikari? CPU?) 모른다.
- **과소발급을 판정하는 하네스.** 발행·소비 실패 시 DB 는 모순이 없어 verify 가 못 잡는다. Redis 잔여 재고 비교를 판정으로 승격하면 된다.
