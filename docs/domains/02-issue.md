# 02. 발급 판정 — 전역 N장, 1인 1매

**맡는 일:** 이 사람에게 한 장을 줘도 되는지 **판정하고 접수**한다. DB 에는 쓰지 않는다 — 기록은 [03. 발급 기록](03-write.md) 이 한다.

![발급 요청의 동기 경로](../diagrams/issue-request-path.svg)

- **① 매진 fast path** — 매진 여부를 Caffeine L1 에 둬서 매진 후 새로고침 폭주가 Redis 까지 안 간다. 캐시 이야기는 [04](04-cache.md).
- **② 발급 정책 조회** — 시작 시각·유효 기간. 캐시 뒤에 있다([04](04-cache.md)).
- **③ `issue.lua`** — `SISMEMBER → GET → DECR → SADD` 를 Redis 안에서 한 덩어리로 돈다. **판정은 여기서 전부 끝난다.** Lua 를 쓰는 이유는 속도가 아니라 이 원자성이다.
- **④ Kafka 발행** — 던지고 곧바로 200. 그래서 **200 은 "발급 완료" 가 아니라 "접수 완료"** 다.
- `issue` 에는 `@Transactional` 이 없다. DB 쓰기가 없는 경로라 지킬 것이 없다(→ [04](04-cache.md) 마지막).

---

## 무엇을 했나

### 과발급 재현 — 원인은 재고 검사가 아니었다

- **문제.** 재고 검사 + 카운터 `++` 인 `naive` 에 5,000 rps × 30s 를 걸자 재고 5,000장에 **7,552장**이 나갔다.
- **시도.** "재고 검사를 안 해서" 라고 가정하지 않고 숫자를 대조했다. 발급 행은 7,552인데 앱의 카운터는 756이었다.
  동시 트랜잭션이 같은 값을 읽고 각자 +1 해서 덮어쓰는 **lost update 로 증가분의 90%가 사라져**, 재고 검사가 한 번도 안 걸렸던 것이다.
- **결과.** `SELECT … FOR UPDATE` 로 정확성을 잡았다. 처리량은 ~263건/s 로 그대로였다.

### Redis Lua 를 붙였는데 빨라지지 않았다

- **문제.** Lua 로 원자 차감을 넣었는데 처리량이 ~252–285건/s — 비관적 락과 차이가 없었다.
- **시도.** 한 번에 고치지 않고 **태그마다 한 가지만** 바꿔 쟀다.

  | 태그 | 바꾼 것 | 처리량 |
  |---|---|---:|
  | `pessimistic` | 비관적 락 | ~263/s |
  | `lua` / `lua-fix` | Redis Lua 원자 차감 | ~285 / ~278/s |
  | `lua-gate` | 거절 요청은 DB 커넥션도 안 잡게 | ~252/s — **이득 없음** |
  | `lua-wb` | `coupon` 단일 행 UPDATE 를 요청 경로에서 제거 | **~2,700/s** |
  | `lua-pool` | Hikari 풀 10 → 50 | **~4,000/s** |

  `lua-gate` 가 이득이 없었던 것으로 병목이 거절 경로가 아니라는 걸 알았다. 선착순이라 **모든 요청이 `coupon` 한 행의 락에 줄을 서고** 있었다.
- **결과.** 모든 단계에서 과발급 판정 OK — 정확성을 내주고 얻은 속도가 아니다.
  **Lua 의 가치는 경합 지점을 DB 밖으로 뺄 수 있다는 것이고, DB 쪽 경합을 같이 없애야만 실현된다.**
- **덤.** `lua` 에서 DB 롤백 시 Redis 재고가 복구되지 않아 **23장이 새는 과소발급**을 찾았다. DB 만 보는 검증은 전부 OK 였다 —
  한 저장소만 보는 검증은 두 저장소 사이의 결함을 구조적으로 못 잡는다. 그래서 검증에 "Redis 잔여 재고 = 총량 − 발급 수" 를 넣었다.

### 쓰기를 큐 뒤로 — 응답 p99 705ms → 5.6ms

- **문제.** 판정 뒤에 동기 INSERT 가 있어 발급 p99 가 705ms.
- **시도.** 인메모리 큐(`@Async`) → Kafka 로 쓰기를 응답 경로 밖으로 뺐다.
- **결과.** p99 **5.6ms**, 열린 모델 5,000 rps 가 처음으로 100% 전달됐다(연결 거부 0).
  대신 200 의 뜻이 바뀌었다 — 응답의 `id` 는 `null` 이고 행은 나중에 들어간다. **성능 최적화가 아니라 API 계약이 바뀐 것**이다.
  병목은 없어진 게 아니라 워커로 옮겨 갔다 → [03](03-write.md).

### 발행 실패 — 200 을 받았는데 사라지는 한 장

- **문제.** Redis 차감 → Kafka 발행은 서로 다른 저장소라 트랜잭션이 없다. 발행 결과를 아무도 안 봐서, 실패하면 **재고는 깎이고 사용자는 "이미 발급됨" 에 남아 영영 거절**됐다. DB 는 모순이 없어 검증이 통과했다.
- **시도.** `docker compose stop kafka` 로 발행 실패를 일부러 냈다. 보상은 **멱등**하게 — `SREM` 이 실제로 지웠을 때만 `INCR` 해서 두 번 불려도 재고가 두 번 안 늘게 했다.
- **결과.** 재현·수정 확인. 그런데 이후 ① 매진 플래그가 생기면서 **보상이 복구한 재고를 그 플래그가 도로 막는** 구조가 됐다.
  보상을 걷어내고 **1장 과소발급을 받아들이는 쪽**을 택했다 — 정상 부하에선 한 번도 안 타는 경로라서. 지금은 503 + ERROR 로그가 유일한 흔적이다.

## 틀렸던 것

- **보상 코드가 있었지만 동작하지 않았다.** 발급자를 기록하는 집합과 지우려는 집합의 키 이름이 달랐다. 호출부만 붙였으면 재고만 돌아오고 사용자는 계속 막힌 반쪽 수정이 될 뻔했다.
- **"에러 로그가 나온다" 를 "처리된다" 로 읽을 뻔했다.** 결함이 있던 시절에도 Spring 이 발행 실패를 ERROR 로 찍고 있었다. 로그는 관측이지 대응이 아니다.

## 남은 과제

- **보상 재도입.** `restore.lua` 가 `sold_out` 플래그까지 지우게 하면 된다. 방법만 기록해 뒀다.
- **아웃박스.** dual write 의 근본 해법. 이 단계에선 과하다고 보고 미뤘다.
- **`lua-pool` ~4,000/s 의 상한 원인 미확정.** Tomcat 스레드 200개가 용의자다.
- **응답 p99 가 앱의 상한인지 모른다.** 부하 상한(5,000 rps)에 먼저 걸렸다. 더 세게 걸면 기존 기록과 비교가 깨진다.
