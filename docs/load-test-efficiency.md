# 효율 트랙 — 캐시로 일의 양을 줄인다 (§18–§22)

`scripts/efficiency/windows/run.ps1` 로 잰 기록. **재는 것은 "같은 결과를 내는 데 드는 일의 양"** 이다
(§18.1). 사용자가 보는 것(정확성·응답시간)이 아니라 자원이 얼마나 타는지를 본다.
그래서 **판정 지표가 p99 가 아니라 카운터(`/metrics/cache`)** 다 — 이유는 §18.3, 근거는 §22.4.

**부하 조건 — 시나리오 둘이 서로 다르다. 가로로 비교하면 안 된다.**

| 시나리오 | 부하 | 쿠폰 | 다루는 절 |
|---|---|---|---|
| ① policy (쿠폰 정보 조회 급증) | 500/s × 30s ≈ 15,000 | 재고 1, `startsAt` 미래 → 전부 `NotStarted` | §19–§21 |
| ② sellout (매진 후 새로고침) | 4,000/s × 30s ≈ 120,000 | 재고 100 을 미리 매진 | §18.2, §22 |

**환경변수 두 개가 결과를 통째로 바꾼다.** `COUPON_CACHE_TTL_MS` / `COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS`.
§18 은 `10000 / 0`, §19 부터는 `1000 / 100` 이고(§21 부터 `COUPON_CACHE_FRESH_MS=500` 추가),
**이 값이 다르면 다른 시스템이라고 봐야 한다**(§19.1, §19.6). `run.ps1` 이 시작할 때 두 값을 찍는다.

**읽는 순서.** `측정 대상 이미지:` 한 줄 → `checks` 100% → 카운터 → 그다음에 지연.
지연으로 판정해야 할 때도 p(99)·max 는 같은 코드를 두 번 재도 40% 씩 흔들리므로
**몸통(p50~p95)** 을 본다(§22.4).

| 파일 | 절 | 담은 것 |
|---|---|---|
| [`load-test-k6.md`](load-test-k6.md) | 환경·TL;DR·§1–§11 | k6 쓰는 법, 출력 읽는 법, 무엇을 믿나 |
| | §6–§12 | 정확성 트랙 — naive · pessimistic · Redis Lua |
| [`load-test-response.md`](load-test-response.md) | §13–§17 | 응답시간 트랙 — 큐 · Kafka · 보상 · 병목 확정 |
| **이 파일** | **§18–§22** | **효율 트랙 — 캐시 · single-flight · SWR · 매진 L1** |

절 번호는 세 파일에 걸쳐 이어진다. 본문에 `12.2`, `15.2.1` 처럼 **파일 표시 없이 나오는 번호**는

## 18. 효율 트랙 — 4-0 기준선 (`cache-4-0`, 2026-08-16)

> **이 절의 수치는 `COUPON_CACHE_TTL_MS=10000`, `COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS=0`
> 에서 쟀다. 4-1 이후(1000 / 100)와 가로로 비교하면 안 된다.**
> 4-1 을 붙이면서 `docker-compose.yml` 이 이 두 값의 기본을 1000 / 100 으로 바꿨다(§19).
> 특히 지연 분포는 조건이 다르면 아예 다른 이야기가 된다 — 카운터(`couponDbReads`)만
> 조건과 무관하게 "요청 수 전부" 라는 의미가 유지된다.
> **`1000/100` 에서 다시 잰 4-0 은 §19.6 에 있다.** 지연이 통째로 달라진다
> (avg 1.43ms → 272.68ms) — 조건이 다르면 다른 시스템이라고 봐야 한다는 실례다.

### 18.1 왜 트랙을 하나 더 만들었나

앞의 두 트랙은 **정확성**(과발급·중복발급)과 **응답시간**(P99)을 잰다. 둘 다 "사용자가 보는 것" 이다.
여기서 재려는 것은 다르다 — **같은 결과를 내는 데 드는 일의 양**이다.
매진된 쿠폰에 새로고침이 쏟아질 때 발급은 어차피 0건이고 응답도 빠르다. 그런데도 요청 하나하나가
DB 를 읽고 Redis Lua 를 돌린다. 사용자 눈에는 안 보이지만 자원은 그만큼 탄다.

그래서 지표를 응답시간이 아니라 **카운터**로 잡았다 (`/metrics/cache`):

| 카운터 | 뜻 |
|---|---|
| `couponDbReads` | 쿠폰 정보를 DB 에서 읽은 횟수 |
| `couponCacheHits` | 캐시로 흡수한 횟수 |
| `soldOutRedisExists` | 매진 판정을 위해 Redis 까지 간 횟수 (= L1 미스) |
| `soldOutFastPathHits` | 매진 판정에 걸려 잘린 횟수 |

> 마지막 줄은 4-0 때 "컨트롤러 진입 직후 잘린 횟수" 로 적어 뒀는데, 실제 구현(4-4)은
> `CouponService.issue` 맨 앞이다. 계획과 구현이 갈라진 자리이고, **그 한 겹 차이가
> `@Transactional` 500µs 로 드러났다** — §22.5.

시나리오는 둘이고 부하 조건이 서로 다르다 (다른 두 트랙의 5,000/s 와도 다르다 — **가로로 비교하면 안 된다**).

| | 조건 | 쿠폰 |
|---|---|---|
| ① 쿠폰 정보 조회 급증 | 500/s × 30s = 15,000 | 재고 1, `startsAt` 미래 → 전부 `NotStarted` |
| ② 매진 후 새로고침 | 4,000/s × 30s = 120,000 | 재고 100 을 미리 매진 |

① 이 `startsAt` 을 미래로 두는 이유: 재고 차감(Lua)이나 Kafka 발행까지 가지 않고
**쿠폰 정보 조회 구간만** 순수하게 부하를 받게 하려는 것이다.

### 18.2 결과 — 모든 요청이 DB 까지 간다

| | 요청 | `couponDbReads` | `couponCacheHits` | `soldOutRedisExists` | `soldOutFastPathHits` | p(99) |
|---|---:|---:|---:|---:|---:|---:|
| ① policy | 15,000 | **15,000** | 0 | 0 | 0 | 1.45ms |
| ② sellout | 119,999 | **119,999** | 0 | 0 | 0 | 5.46ms |

**`couponDbReads` 가 요청 수와 정확히 같다.** 캐시가 없으니 당연하지만, 이것이 기준선이다.
②가 특히 그렇다 — **이미 매진된 쿠폰인데 12만 건이 전부 DB 를 읽고 Lua 까지 들어가서
`-1`(매진)을 받아 나온다.** 아무것도 바뀌지 않을 요청 12만 건이 전 구간을 완주한다.

검사는 두 시나리오 모두 `checks 100%` (`route exists (not 404)`, `connected (not status 0)`).
`status_conn_error` 는 **출력에 나타나지도 않았다 = 0** — 4,000/s 에서 연결 거부가 한 건도 없었다.
응답시간 트랙이 5,000/s 에서 15~27% 를 잃던 것(§12.7.3)과 대조된다.
`vus max=15` 였다. 백프레셔가 전혀 없다.

`http_req_failed 100%` 는 정상이다. 두 시나리오 모두 **409 가 정상 응답**이고
(`NotStarted` / `SOLD_OUT`, `support/DomainException.kt`) k6 은 4xx 를 실패로 센다.
읽어야 하는 것은 `status_409_*` 쪽이다.

### 18.3 이 트랙에서 p99 는 아직 지표가 아니다

**캐시가 아예 없는 4-0 인데 두 시나리오 모두 threshold 를 통과했다**
(①`p(99)<200` → 1.45ms, ②`p(99)<100` → 5.46ms).

DB 조회가 1ms 남짓이라 캐시를 붙여도 줄어들 여지가 없기 때문이다.
`CouponService.issue` 에 그 지점의 주석이 남아 있다 — "로컬은 너무 빨라서 100ms 늦춰서 테스트 해보려 함".
`COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS`(기본 0)를 켜야 조회 비용이 응답시간에 드러난다.
`COUPON_CACHE_TTL_MS` 도 기본 10000 이라 30초 동안 만료가 세 번뿐이고, stampede 윈도우가 그만큼 좁다.

**그래서 이 트랙의 판정은 카운터로 한다.** p99 만 보면 개선을 놓치거나(4-1),
없는 개선을 봤다고 오독한다. 4-2 의 fast-path 효과도 p99 가 아니라
`soldOutFastPathHits` 가 요청 수에 수렴하는 것으로 확인될 것이다.

> **이 원칙의 근거가 §22.4 에 자료로 남았다.** 같은 이미지를 두 번 잰 결과
> 카운터는 네 라운드 전부 같은 값이었는데 p(99) 는 4.52 / 2.58ms 로 **43% 흔들렸다.**
> p99 로 판정했다면 같은 코드를 두 번 재고 "1.75배 좋아졌다" 는 결론이 나온다.

> **덧 (2026-08-16, 4-1 측정 후).** 위 진단은 맞았고, 그래서 4-1 을 붙이면서
> `COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS` 를 100 으로 켰다. 이제 조회 비용이 응답시간에
> 드러나므로 **p99 도 지표가 됐다.** 다만 판정 기준은 그대로다 — single-flight 이전에는
> p99 가 stampede 윈도우 때문에 계속 튀므로, 개선 여부는 여전히 `couponDbReads` 로 본다(§19.4).

### 18.4 음수 지연 샘플이 또 나왔다

②에서 `issue_latency`의 `min = -426349244ns` (-426ms). §13.2 에서 한 번 겪고 원인 미확정으로
남겨 둔 것과 같은 현상이다(컨테이너 클럭으로 추정). 119,999 샘플 중 하나라 avg 를 3.5µs 밀 뿐이고
p99 는 영향이 없다. **결함으로 읽지 말 것** — 다만 `min` 이 음수인 것 자체는 매번 확인하고 넘어간다.

### 18.5 다음

4-1 은 쿠폰 정보 조회를 DB 가 아니라 **Redis 캐시**로 받는다. 여기서 움직여야 하는 것은
`couponDbReads` 이고, `couponCacheHits` 와의 합이 요청 수 근처를 유지해야 한다
(합이 모자라면 어딘가에서 요청이 새는 것이다).

## 19. 쿠폰 정보 조회를 Redis 로 — `rediscache-4-1` (2026-08-16)

### 19.1 측정 조건이 바뀌었다 — 결과보다 먼저 읽을 것

`docker-compose.yml` 의 `coupon-service` 에 두 줄이 들어왔다.

```yaml
COUPON_CACHE_TTL_MS: ${COUPON_CACHE_TTL_MS:-1000}
COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS: ${COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS:-100}
```

§18 은 `10000 / 0`, 여기는 `1000 / 100` 이다. **지연 분포는 서로 비교할 수 없다.**
`latency=0` 이면 DB 조회가 1ms 라 캐시를 붙여도 응답시간이 줄어들 여지가 없어서,
캐시 효과를 응답시간으로 보려면 조회에 비용을 심어야 했다.

이 두 값을 로그에 안 남겨서 실제로 한 번 오독할 뻔했다 — p99 가 1.45ms → 102ms 로
**나빠진 것처럼** 보였는데 회귀가 아니라 워크로드가 바뀐 것이었다.
그 뒤 `efficiency/windows/run.ps1` 이 시작할 때 두 값을 모두 찍도록 고쳤다.

### 19.2 무엇을 바꿨나

| | 4-0 | 4-1 |
|---|---|---|
| 조회 경로 | `CouponService.issue` 가 직접 `couponRepository.findById` | `CouponIssuePolicyReader` → `CouponCacheRepository.getIssuePolicyOrLoad` |
| 캐시 | 없음 | Redis, 키 `coupon:{id}:issue-policy`, read-through |
| 캐싱 대상 | — | `CouponPolicy`(`startsAt`, `validityDays`)**만**. 재고는 캐싱하지 않는다 |

재고를 안 넣은 것이 중요하다. 재고는 Lua 가 원자적으로 다루는 값이라 캐싱하는 순간
과발급이 돌아온다. **캐싱해도 되는 것은 잘 안 변하고 틀려도 치명적이지 않은 것뿐이다.**

카운터를 올리는 곳도 `CouponCacheRepository.getOrLoad` 한 군데로 모였다
(미스면 `couponDbReads`, 히트면 `couponCacheHits`). 그래서 둘의 합은 요청 수와 정확히 맞아야 한다.

> **이 불변식은 4-2 까지만 성립한다.** 조회가 전부 요청 스레드에서 일어나기 때문이다.
> SWR(4.3)부터는 백그라운드 갱신이 **요청에 안 붙는 `couponDbReads`** 를 만들어
> 합이 요청 수를 넘어간다(15,049 vs 15,001). 바뀐 형태는 §21.4 에 적어 뒀다.

### 19.3 결과 (steady 라운드, 500/s × 30s = 15,000)

| | `couponDbReads` | `couponCacheHits` | avg | p(50) | p(90) | p(95) | p(99) |
|---|---:|---:|---:|---:|---:|---:|---:|
| 4-1 | **1,250** | 13,750 | 9.45ms | 1.04ms | 1.39ms | **101.83ms** | **102.37ms** |

`1,250 + 13,750 = 15,000` — 정확히 맞는다. 새는 요청 없음.
checks 100%, `status_conn_error` 0(출력에 아예 안 나타났다), `vus max=18`.

**DB 조회가 15,000 → 1,250 으로 12배 줄었다.** 캐시는 제대로 먹었다.

### 19.4 그런데 1,250 은 거의 전부 stampede다 — 산수가 맞아떨어진다

이론적으로 필요한 DB 조회는 **TTL 만료 한 번에 1건**뿐이다. 그런데 50배를 읽고 있다.
`getOrLoad` 에 single-flight 가 없어서 만료 직후 몰린 요청이 **전부** 로더를 탄다.

- 로더 = `Thread.sleep(100)` + `findById` → **미스 창 100ms**
- 500/s × 0.1s = **미스 50건/사이클**
- `opsForValue().set(key, …, Duration)` 은 **쓸 때마다 TTL 을 재시작한다.**
  마지막 미스가 t≈100ms 에 도착해 t≈200ms 에 쓰므로 다음 만료는 1,000ms 가 아니라
  **t≈1,200ms** → **사이클 ≈ 1.2s**
- 30s ÷ 1.2s = **25 사이클**

**25 × 50 = 1,250.** 워밍업·본측정 두 라운드 모두 정확히 1,250 이 나왔다.

지연 분포도 같은 모델로 풀린다. 미스 비율 1250/15000 = **8.33%** 이므로 경계는 p91.7 —
그래서 p(90)=1.39ms(히트)와 p(95)=101.83ms(미스)로 깨끗하게 갈린다.
평균도 `0.0833 × 102 + 0.9167 × 1.1 ≈ 9.5ms` 로 실측 9.45ms 와 맞는다.

**"TTL 이 쓰기마다 재시작된다" 는 놓치기 쉬운 지점이다.** 사이클을 1.0s 로 잡으면
30 사이클 × 50 = 1,500 이 나와서 실측과 안 맞는다. 미스 50건이 *각자* 캐시를 쓰고,
그중 마지막 쓰기가 TTL 시계를 다시 돌린다.

### 19.5 다음 단계에서 움직여야 하는 숫자

| | `couponDbReads` | p(99) | |
|---|---:|---|---|
| 4-1a (이 절) | 1,250 | ~102ms | 실측 |
| single-flight | ~25 (사이클당 1건) | 여전히 ~100ms | **예상 → §20 에서 27 / 103.11ms 로 확인됨** |
| SWR | 그대로 | ~1ms | **예상 → §21 에서 49 / 1.66ms.** p99 는 맞았고 조회 수는 빗나갔다 |

**single-flight 를 p99 로 판정하면 "효과 없다" 는 정반대 결론이 나온다.** DB 조회는
사이클당 1건으로 줄지만, 로더를 기다리는 나머지 49건의 대기는 그대로 남기 때문이다.
지연이 사라지는 것은 stale 을 내주고 뒤에서 갱신하는 SWR 에서다.

> 이 예상은 §20 에서 그대로 맞았다 — 조회 1,250 → **27**(46배), p(99) 102.37 → **103.11ms**(제자리).

### 19.6 4-0 을 같은 조건으로 다시 쟀다 — 예상보다 훨씬 나빴다

`.\build-and-run.ps1 -Tag cache-4-0 -NoBuild` 로 되돌려 `1000/100` 에서 다시 쟀다
(`cache-4-0` 이미지의 `CouponService` 도 `simulatedLoadLatencyMs` 를 `Thread.sleep` 하므로
새 compose 설정이 그대로 먹는다). 둘 다 steady 라운드:

| | `couponDbReads` | avg | p(50) | p(90) | p(95) | p(99) | max | k6 `vus max` |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `cache-4-0` | 15,001 | 272.68ms | 257.87ms | 427.18ms | 461.44ms | 747.91ms | 1.63s | **238** |
| `rediscache-4-1` | 1,250 | 9.45ms | 1.04ms | 1.39ms | 101.83ms | 102.37ms | 107.39ms | 18 |
| 배수 | **12.0×** | **28.9×** | 248× | — | — | 7.3× | — | — |

`p(99)<200` 은 4-0 에서 깨진다(exit 99). 캐시가 없으니 정상이다.

**예상은 avg ≈ 102ms 였는데 272.68ms 가 나왔다. 2.7배 빗나갔다.**
"전 요청이 100ms 를 자니까 응답도 100ms 언저리" 라는 계산이 틀렸다 — 대기가 붙었다.

### 19.7 4-0 은 커넥션 풀 포화 상태로 돌고 있었다

`vus max=238` 이 단서다. 100ms 씩 자는 요청이 500/s 로 들어오면 리틀의 법칙상
**동시 50건**이면 충분하다. 238건이 물려 있었다는 것은 **188건쯤이 뭔가를 기다리고 있었다**는 뜻이다.

용량이 50 인 자원은 이 시스템에 하나뿐이다 — **Hikari 풀(`maximum-pool-size: 50`, §12.7).**

`CouponService.issue` 는 `@Transactional` 이고 `Thread.sleep` 이 그 **안에** 있다.
Hikari 의 `auto-commit` 이 기본값 `true` 라 Spring Boot 가
`hibernate.connection.provider_disables_autocommit` 을 켜지 않고, 그러면 Hibernate 는
트랜잭션 시작 시점에 `setAutoCommit(false)` 를 하려고 **커넥션을 미리 잡는다.**
즉 100ms 를 자는 동안 커넥션을 쥐고 있다.

- 4-0: 500/s × 0.1s = **동시 50건이 커넥션을 점유** → 풀 50 에 정확히 ρ = 1.0.
  포화 지점이라 대기가 무한정 쌓이는 구간이고, 실제로 지연이 튀고 불안정하다
  (워밍업 avg 342.72ms / p99 1.05s → 본측정 272.68ms / p99 747.91ms 로 라운드마다 크게 다르다)
- 4-1: 미스만 로더를 타므로 1,250건 ÷ 30s × 0.1s = **동시 4.2건.** ρ ≈ 0.08 이라 대기가 없고,
  그래서 미스 지연이 정확히 100ms 대(101.83ms)로 나온다

**4-1 의 미스 지연이 딱 100ms 라는 것 자체가 이 해석의 근거다.** 같은 100ms sleep 인데
4-0 에서는 272ms, 4-1 에서는 102ms 다. 차이는 대기뿐이고, 대기를 만든 것은 점유율이다.

**Tomcat 스레드(기본 200)는 범인이 아니다.** 50개만 자고 있으면 되므로 여유가 있고,
용량이 238 보다 커서 관측된 동시성을 설명하지 못한다.

> **미확정.** 위는 산수와 정황으로 좁힌 것이지 직접 계측한 것이 아니다.
> `SHOW GLOBAL STATUS LIKE 'Max_used_connections'` 는 **증거가 되지 못한다** —
> Hikari 의 `minimumIdle` 기본값이 `maximumPoolSize` 라 부하와 무관하게 50개를 열어 두기 때문이다
> (실제로 51 이 나왔지만 §7 의 확인 표가 말하는 "설정이 먹었나" 이상은 못 말해 준다).
> 확인하려면 풀만 키워서 다시 재면 된다 — 대기가 원인이라면 avg 가 100ms 대로 내려가야 한다:
>
> ```powershell
> $env:SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE = '200'
> .\scripts\efficiency\windows\run.ps1 -Scenario policy -Once
> ```
>
> 단, 이 값을 바꾼 측정은 다른 기록과 비교하면 안 된다. 원인 확인용으로만 쓴다.
>
> **확인됐다 (§22.5, 2026-08-17).** 풀을 키우는 대신 반대쪽에서 잡혔다 —
> `@Transactional` 을 떼자 **DB 를 한 줄도 안 읽는 요청의 med 가 500µs 내려갔다.**
> 트랜잭션이 시작 시점에 커넥션을 잡는다는 것이 이걸로 확인된다. 500µs 라는 크기는
> 풀 체크아웃만으로는 설명이 안 되고 `SET autocommit` / `rollback` 왕복까지 가야 맞는데,
> **거기까지는 여전히 산수다.**

### 19.8 그래서 캐시가 실제로 산 것

DB 조회 12배 감소는 표면이다. **진짜 효과는 커넥션 풀 점유율을 ρ 1.0 에서 0.08 로 내린 것**이고,
avg 가 28.9배 좋아진 것의 대부분이 거기서 온다. 조회를 캐시로 흡수하면
그 요청이 잡고 있던 **커넥션·트랜잭션까지 같이 사라진다** — 아껴진 것은 DB 왕복이 아니라 점유 시간이다.

뒤집어 말하면 **4-0 의 수치는 "DB 가 느려서" 가 아니라 "포화라서" 나쁜 것**이고,
같은 이유로 이 조건에서의 4-0 p99 는 부하 조건에 매우 민감하다. rate 를 조금만 낮춰도
크게 달라진다 — 다른 rate 로 잰 값과 나란히 놓지 말 것.

## 20. Single Flight — `single-flight-4.2` (2026-08-16)

### 20.1 첫 실행은 측정이 아니라 버그였다 — 그리고 `checks` 가 못 잡았다

고치기 전 실행에서 이런 값이 나왔다.

| | 값 |
|---|---|
| `couponDbReads` / `couponCacheHits` | **0 / 0** |
| 상태 코드 | `status_other` 15,001 (`status_409_not_started` 가 아니다) |
| max 지연 | 6.96ms — **100ms 로더가 한 번도 안 돌았다** |
| k6 `checks` | **100% 통과** |

원인은 Lua 파일명이었다. 디스크에는 `cach-single-flight.lua`, 코드는
`ClassPathResource("lua/cache-single-flight.lua")`. `RedisScript.of(...)` 는 리소스를
**지연 로딩**하므로 **앱은 정상 기동하고 `/metrics/cache` 도 응답한다** — 러너의 preflight 가
통과한 이유다. 터지는 것은 `execute` 가 스크립트 본문을 읽는 매 요청이다.

던져지는 지점이 `getOrLoad` 의 `when(result[0])` **이전**이라 카운터를 하나도 못 올렸고,
`DomainException` 이 아니라 `GlobalExceptionHandler` 를 안 타고 500 이 됐다.

**`checks` 는 이것을 못 잡았다.** 당시 검사는 `!== 404` 와 `!== 0` 뿐이었고 500 은 둘 다 통과한다.
§8.2 에서 한 번 당한 것과 같은 유형이 다른 옷을 입고 돌아온 것이다.
잡아낸 것은 **`couponDbReads + couponCacheHits = 요청 수`** 불변식이었다.

그래서 두 k6 스크립트에 `'no server error (not 5xx)'` 를 추가했다. 그 실행이었다면
`checks 66%` 로 즉시 드러났다.

> **교훈:** 성공 검사는 "무엇이 실패인가" 를 다 적어 둔 만큼만 유효하다.
> 카운터 합처럼 **다른 축에서 오는 불변식**을 하나 더 두는 것이 그래서 값어치를 한다.

### 20.2 결과 (steady, 500/s × 30s = 15,001, TTL 1000 / latency 100)

| 태그 | `couponDbReads` | avg | p(50) | p(90) | p(95) | p(99) | max |
|---|---:|---:|---:|---:|---:|---:|---:|
| `cache-4-0` | 15,001 | 272.68ms | 257.87ms | 427.18ms | 461.44ms | 747.91ms | 1.63s |
| `rediscache-4-1` | 1,250 | 9.45ms | 1.04ms | 1.39ms | 101.83ms | 102.37ms | 107.39ms |
| **`single-flight-4.2`** | **27** | 6.88ms | 1.07ms | 1.68ms | **62.18ms** | 103.11ms | 125.31ms |

`27 + 14,974 = 15,001`. checks 세 항목 모두 100%.

**DB 조회가 1,250 → 27 로 46배 줄었다.** 4-0 기준으로는 555배다.

### 20.3 27 은 이론적 바닥이다 — 그리고 사이클이 짧아졌다

§19.4 의 모델이 그대로 이어진다. 달라진 것은 **캐시를 쓰는 주체가 50명에서 1명이 된 것**이고,
그 때문에 TTL 시계가 다시 도는 시점이 앞당겨진다.

| | 캐시를 쓰는 시점 | 사이클 | 30초 안의 사이클 | 사이클당 DB 조회 | 합계 |
|---|---|---|---:|---:|---:|
| 4-1a | 마지막 미스가 t≈200ms | 1.2s | 25 | 50 | **1,250** |
| 4-1b | 로더 하나가 t≈100ms | **1.1s** | **27** | **1** | **27** |

30s ÷ 1.1s = 27.3 → **27**. 실측 27(steady) / 28(warmup) 과 맞는다.
**사이클 수는 오히려 늘었는데(25 → 27) 총 조회는 46배 줄었다** — single-flight 가 없앤 것은
"만료가 자주 오는 것" 이 아니라 "만료 한 번에 몰려 들어가는 것" 이기 때문이다.

즉 **27 은 "많이 줄었다" 가 아니라 이 TTL 에서 도달 가능한 하한 그 자체다.**
더 줄이려면 캐시 적중률이 아니라 TTL 을 건드려야 한다.

### 20.4 p99 는 그대로다 — 예상대로고, 그래서 판정을 카운터로 한다

p(99) 102.37ms → **103.11ms.** 사실상 변화가 없다.
**여기서 p99 만 봤다면 "single-flight 는 효과가 없다" 는 정반대 결론이 나온다.**

이유는 §19.5 에 미리 적어 둔 그대로다. 만료 창 100ms 안에 도착한 50건 중
**로더는 1건뿐이지만 나머지 49건은 여전히 기다린다.** DB 는 안 때리지만 사용자는 그만큼 기다린다.

다만 **꼬리의 모양은 좋아졌다.**

- p(95): 101.83ms → **62.18ms**. 4-1a 에서는 미스 50건이 *각자* 100ms 를 온전히 썼지만,
  4-1b 의 대기자는 **로더가 끝날 때까지 남은 시간만** 기다린다. 만료 직후 도착한 요청은 100ms,
  90ms 뒤에 도착한 요청은 10ms — 대기 시간이 0~120ms 에 고르게 퍼진다
- avg: 9.45ms → 6.88ms
- 그런데 p(99)·max 는 오히려 조금 올라갔다(107.39 → 125.31ms). **20ms 백오프 때문이다** —
  캐시가 채워진 직후 폴링을 막 놓친 대기자는 최대 한 텀(20ms)을 더 잔다.
  `100ms + 20ms + 오버헤드 ≈ 125ms` 로 `WAIT_BACKOFF_MS = 20` 이 실측에 그대로 보인다

산수로 확인해 두면: 대기 창에 걸리는 비율은 사이클당 50건 ÷ 550건(=500/s × 1.1s) = **9.1%** 다.
그래서 p(90)=1.68ms 가 아직 캐시 히트이고, p(95)·p(99) 가 대기 분포 위에 놓인다.
평균도 `0.909 × 1.1ms + 0.091 × 60ms ≈ 6.5ms` 로 실측 6.88ms 와 맞는다.

### 20.5 다음 — SWR 이 건드릴 것은 이 49건이다

| | `couponDbReads` | p(99) |
|---|---:|---|
| 4-1a | 1,250 | ~102ms |
| **4-1b (지금)** | **27** | ~103ms |
| 4-1c SWR | ~27 (그대로) | **~1ms 여야 한다** |

SWR 은 만료된 값을 **일단 내주고** 뒤에서 갱신하므로 대기자가 사라진다.
`couponDbReads` 는 이미 바닥이라 더 내려갈 곳이 없다 — **다음 단계의 판정 지표는 p99 다.**
이 트랙에서 처음으로 지연이 주 지표가 되는 구간이다.

> **§21 결과.** p99 는 맞았다(1.66ms). 조회 수는 틀렸다 — 27 이 아니라 **49** 다.
> "`couponDbReads` 는 더 내려갈 곳이 없다" 까지는 맞지만 **올라갈 곳은 있었다.**
> 갱신 주기를 TTL(1000ms)이 아니라 `fresh-ms`(500ms)가 잡기 때문이다(§21.4).

## 21. Stale-While-Revalidate — `swr-4.3` (2026-08-16)

### 21.1 또 첫 실행이 측정이 아니라 버그였다 — 이번엔 Lua ARGV 하나

`/metrics/cache` 카운터 4개가 전부 0 이었다. §20.1 과 증상이 같아서 같은 자리를 봤는데,
이번 원인은 파일명이 아니라 **인자 개수**였다.

```
ERR Lua redis lib command arguments must be strings or integers
script: 04007ac6…, on @user_script:10.
```

`cache-single-flight-swr.lua` 의 계약은 `ARGV = nowMs, freshMs, lockToken, lockTtlMs` (4개)인데
Kotlin 이 `now, properties.freshMs, LOCK_TTL_MS` (3개)만 넘겼다. `token` 이 빠져서
`ARGV[3]`(락 토큰 자리)에 `3000` 이 들어가고 `ARGV[4]` 는 nil →
`SET KEYS[2] ARGV[3] NX PX nil` 에서 매번 터졌다.
캐시가 빈 첫 요청은 무조건 이 SET 분기를 타므로 **예외 없이 전 요청이 실패**한다.

던져지는 지점이 `when(result[0])` 이전이라 카운터가 하나도 안 올라가는 것까지 §20.1 과 같다.
다른 점은 **이번엔 500 이 나갔다는 것** — §20.1 뒤에 추가해 둔 `'no server error (not 5xx)'`
검사가 덮는 실패 모드다. 진단은 컨테이너 로그 한 줄(`@user_script:10`)로 끝났다.

> **KEYS/ARGV 계약은 스크립트 헤더 주석에만 있고 컴파일러가 안 본다.**
> `runForStrings(script, keys, vararg args)` 는 개수를 세지 않으므로 하나 빠져도 조용히 통과하고,
> 터지는 것은 Redis 안이다. Lua 를 고칠 때 **헤더 주석과 호출부를 나란히 놓고 세는 것**이 유일한 방어다.

### 21.2 결과 (steady, 500/s × 30s = 15,001, TTL 1000 / fresh 500 / latency 100)

| 태그 | `couponDbReads` | avg | p(50) | p(90) | p(95) | p(99) | max | `vus max` |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `cache-4-0` | 15,001 | 272.68ms | 257.87ms | 427.18ms | 461.44ms | 747.91ms | 1.63s | 238 |
| `rediscache-4-1` | 1,250 | 9.45ms | 1.04ms | 1.39ms | 101.83ms | 102.37ms | 107.39ms | 18 |
| `single-flight-4.2` | 27 | 6.88ms | 1.07ms | 1.68ms | 62.18ms | 103.11ms | 125.31ms | — |
| **`swr-4.3`** | **49** | **1.35ms** | 1.11ms | 1.26ms | **1.33ms** | **1.66ms** | 110.19ms | **2** |

checks 세 항목 모두 100%, `status_409_not_started` 15,001, `status_conn_error` 0.

**p(99) 103.11 → 1.66ms (62배).** §19.5 에 "~1ms" 로 적어 둔 예상 안에 들어왔다.

### 21.3 진짜 결과는 배수가 아니라 분포의 모양이다

4-2 의 꼬리에는 절벽이 있었다 — p(90) 1.68ms 인데 p(95) 62.18ms. 만료 창에 걸린 9.1% 가
20ms 백오프로 폴링하며 대기하던 자리다(§20.4). 4-3 은 **p(90) 1.26 → p(99) 1.66ms 로 평평하다.**

**대기자가 0 이 됐다.** stale 을 즉시 내주고 갱신을 백그라운드 스레드로 넘겼으니
어떤 요청도 로더를 기다리지 않는다. 없앤 것은 "대기 시간" 이 아니라 **대기라는 상태 자체**다.

`vus max` 가 이 이야기를 한 번 더 한다: **238 → 18 → 2.** 리틀의 법칙으로
500/s × 1.35ms = 동시 0.7건이니 2 가 맞다. 시스템 안에 머무는 요청이 사실상 없다 —
§19.7 에서 커넥션 풀 포화(ρ=1.0)로 시작한 이 트랙이 여기서 반대편 끝에 닿았다.

### 21.4 `couponDbReads` 27 → 49 는 회귀가 아니라 노브다

DB 조회가 1.8배 **늘었다.** SWR 자체의 비용이 아니라 갱신 주기를 무엇이 잡느냐가 바뀐 것이다.

| | 갱신을 트리거하는 것 | 사이클 | 30초 안의 사이클 | 실측 |
|---|---|---|---:|---:|
| 4-2 | TTL 만료 1,000ms + 로더 100ms | 1.1s | 27 | 27 |
| **4-3** | **`fresh-ms` 500ms** + 로더 100ms | **0.6s** | **50** | **48** |

`49 = 콜드 LOAD 1 + 백그라운드 갱신 48`. 워밍업 48 / 본측정 49 로 **라운드 간 차이가 1건**이다 —
카운터는 JIT 노이즈를 안 탄다는 증거이기도 하다.

`fresh-ms` 를 1000 으로 올리면 27 근처로 돌아온다. 그러면 안 되는 이유가 있다:
지금 구조는 **갱신이 만료보다 500ms 앞서 TTL 을 다시 밀어주는** 것이라
트래픽이 끊기지 않는 한 키가 실제로 만료되지 않는다. `fresh = ttl` 로 두면 그 여유가 사라지고,
로더가 늦는 순간 키가 비어 `LOAD`/`WAIT` 경로 — 즉 4-2 의 대기가 돌아온다.
**`ttl - fresh` 는 로더가 늦어도 되는 예산이다.** 여기서는 500ms.

거래를 한 줄로: **DB 조회 22건을 더 쓰고 대기자 ~1,350건(사이클 27 × 50)을 없앴다.**

**그리고 여기서 §19.2 의 불변식이 처음 깨진다.**

```
couponDbReads + couponCacheHits = 15,049 ≠ 15,001   ← 버그가 아니다
```

백그라운드 갱신이 **요청에 안 붙는 DB 조회**를 만들기 때문이다. 새 형태는 이렇다.

```
couponCacheHits + 포그라운드 LOAD = 요청 수
초과분 = STALE_REFRESH 횟수 = 48
```

**§20.1 을 잡아낸 것이 바로 이 불변식이었으므로 그냥 넘기면 안 된다.** 지금은
포그라운드/백그라운드 조회를 나누는 카운터가 없어서 초과분을 역산해야 읽힌다.
다음에 카운터를 건드릴 일이 있으면 `couponDbReadsBackground` 를 하나 쪼개 두는 편이 낫다.

### 21.5 max 110ms 와 워밍업

- **max 110.19ms 는 라운드 첫 요청 하나.** `run.ps1` 은 Redis 를 비우지 않지만 워밍업↔본측정
  사이 간격이 TTL 1초보다 훨씬 길어 키가 만료된 채로 시작한다. 로더 지연 100ms 가 그대로 찍힌 값이다.
  **TTL 을 10000 으로 되돌려 재면 이 콜드 LOAD 가 사라져 max 가 달라진다** — 조건을 같이 읽을 것.
- **워밍업 폐기 설계가 또 값을 했다.** 워밍업 p(99) 18.79ms / max 323.73ms → 본측정 1.66 / 110.19ms.
  안 버렸으면 "SWR 이 p99 를 18ms 로 만들었다" 는 11배 나쁜 숫자를 기록했다. §14.4 와 같은 자리다.

### 21.6 다음 — 매진 즉시 차단 (Caffeine L1)

여기까지가 **쿠폰 정보 조회**(policy 시나리오)다. 다음은 두 번째 시나리오, **매진 후 새로고침**이고
바꾸는 것은 캐시 계층이 아니라 **차단 지점**이다. 판정 지표도 다시 카운터로 돌아간다
(`soldOutRedisExists` / `soldOutFastPathHits`). 지금까지 이 둘이 계속 0 인 것은 결함이 아니라
**올리는 코드가 아직 없어서**다.

계획은 Redis 앞에 **Caffeine L1**(로컬 인메모리)을 두어 매진 판정을 프로세스 안에서 끝내는 것이다.
현재 4-3 기준으로 매진된 쿠폰에 오는 요청은 여전히 전 구간을 완주한다.

**측정에 들어가기 전에 걸리는 것 하나.** §19–21 은 전부 `-Scenario policy` 로만 쟀다.
sellout 시나리오의 마지막 기록은 §18.2 의 `cache-4-0`(119,999건)인데 **그건 `10000 / 0` 조건**이다.
지금 조건(`1000 / 100 / fresh 500`)의 sellout 기준선이 아예 없다.
L1 을 붙이기 **전에** `-Scenario sellout` 을 4-3 에서 한 번 재서 기준선을 만들어야
개선분을 L1 의 것으로 돌릴 수 있다. 안 그러면 §19.1 에서 한 번 당한
"워크로드가 바뀐 것을 성능 변화로 읽는" 오독이 그대로 반복된다.

| | `couponDbReads` | `soldOutRedisExists` | `soldOutFastPathHits` |
|---|---|---|---|
| 4-3 sellout (미측정) | ? | 0 | 0 |
| 4-4 Caffeine L1 | 그대로여야 한다 | 줄어야 한다 | **요청 수에 수렴해야 한다** |

> **§22 결과.** 기준선은 먼저 떴다(4-3 sellout = 49). 예상 셋 중 둘은 맞고 하나는 빗나갔다 —
> `couponDbReads` 는 "그대로" 가 아니라 **0** 이 됐고(fast path 가 정책 조회 경로 앞에서 자른다),
> `soldOutFastPathHits` 는 "수렴" 이 아니라 **요청 수와 정확히 일치**했다.

## 22. 매진 즉시 차단 — `l1cache` (2026-08-17)

이 절만 **시나리오 ②(sellout, 4,000/s × 30s)** 다. §19~§21 은 전부 ①(policy, 500/s)이었다.
**세로로도 가로로도 §19~§21 과 비교하면 안 된다.**

### 22.1 무엇을 바꿨나

| | 4-3 까지 | 4-4 |
|---|---|---|
| 매진 판정 | `issue.lua` 까지 가서 `0` 을 받아온다 | 요청 맨 앞 **Caffeine L1** |
| 플래그 | 없음 | `issue.lua` 가 **마지막 한 장이 나갈 때** `coupon:{id}:sold_out` SET (차감과 원자적) |
| Redis 확인 | — | L1 미스일 때만 `EXISTS` (`SoldOutRedisRepository`) |
| 재고 보상 | 있음 | **제거** ([`architecture.md` §4](architecture.md)) |

강의 코드와 일곱 항목을 대조했고 **전부 일치한다.** 유일하게 달랐던 것은 우리가 3-3 에서
강의보다 더 만들었던 보상(§15·§17)이고, 그것을 4-4 에서 지우면서 오히려 강의와 같아졌다.

### 22.2 결과 (steady, 4,000/s × 30s ≈ 120,000)

| | `couponDbReads` | `couponCacheHits` | `soldOutRedisExists` | `soldOutFastPathHits` |
|---|---:|---:|---:|---:|
| `swr-4.3` | 49 | 120,001 | 0 | 0 |
| **`l1cache`** | **0** | **0** | **30** | **120,001** |

**`soldOutFastPathHits` 가 요청 수와 정확히 같다.** §18.3 에 "수렴해야 한다" 고 적었는데
수렴이 아니라 일치다 — 단 한 건도 fast path 를 안 지나간 요청이 없다.

**`soldOutRedisExists = 30` 은 이론값 그대로다.** `fast-path-ttl-ms = 1000`, 측정 30초, 키 1개
→ Caffeine 로드 30회. 워밍업 포함 **네 라운드 전부 정확히 30** 이었다.

`couponDbReads`·`couponCacheHits` 가 둘 다 0 인 것은 fast path 가 `couponIssuePolicyReader`
**앞에서** 자르기 때문이다. 정책 캐시는 이 시나리오에서 아예 안 돌아간다.

### 22.3 L1 이 산 것은 지연이 아니라 Redis 여유다

| | Redis 명령 | 12만 건 중 Redis 를 본 것 |
|---|---:|---:|
| `swr-4.3` | 요청당 2회 ≈ **8,300/s** | 120,002건 |
| `l1cache` | 30회 / 30초 = **1/s** | **30건** |

**흡수율 99.975%.** 119,971건이 프로세스 밖으로 한 발짝도 안 나갔다.

그런데 **Redis 부하가 8,300/s → 1/s 로 사라지는 동안 지연은 1.7배밖에 안 좋아졌다**
(med 1.40ms → 834µs, 아래 22.5 의 중간 단계 값). Redis 가 병목이 아니었기 때문이다
(`vus max 34` — 대기가 거의 없다). §19.8 에서 캐시가 커넥션 풀 포화를 푼 것과는 성격이 다르다.
**여기서 산 것은 지금 빨라진 것이 아니라 Redis 가 다른 일을 할 수 있게 된 것이다.**

### 22.4 재현성 — 카운터는 4/4 일치, 꼬리는 매번 다르다

같은 이미지·같은 조건으로 두 번 잰 steady 라운드.

| | 1차 | 2차 | 차이 |
|---|---:|---:|---:|
| p(50) | 843.99µs | 833.84µs | 1.2% |
| p(90) | 966.64µs | 943.79µs | 2.4% |
| p(95) | 1.03ms | 992.44µs | 3.8% |
| **p(99)** | **4.52ms** | **2.58ms** | **43%** |
| **max** | **50.52ms** | **31.97ms** | **37%** |
| `soldOutRedisExists` | 30 | 30 | **0%** |
| `soldOutFastPathHits` | 요청 수 | 요청 수 | **0%** |

**몸통은 4% 안에서 재현되고 꼬리는 40% 씩 흔들린다.**
§18.3 의 "이 트랙의 판정은 카운터로 한다" 와 §15.2.1 의 "단일 실행끼리의 p99 차이는
판정 근거가 못 된다" 가 한 표에 같이 들어 있다 —
**p99 로 판정했다면 같은 이미지를 두 번 재고 "1.75배 좋아졌다" 고 쓸 뻔했다.**

### 22.5 그리고 `@Transactional` 이 36% 였다

4-4 를 정리하다 `CouponService.issue` 의 `@Transactional` 을 떼고 한 변수만 바꿔 다시 쟀다.
**카운터 네 값이 전부 그대로**여서 실험이 깨끗하게 성립했다.

| steady | `@Transactional` 있음 | 없음 | 줄어든 양 |
|---|---:|---:|---:|
| avg | 907.33µs | 387.67µs | −520µs |
| **p(50)** | 833.84µs | **334.17µs** | **−500µs** |
| p(90) | 943.79µs | 413.58µs | −530µs |
| p(95) | 992.44µs | 451.45µs | −541µs |
| p(99) | 2.58ms | 1.74ms | −840µs |
| max | 31.97ms | 32.26ms | ±0 |
| `vus max` | 7 | 3 | |

**p50·p90·p95 가 전부 500~540µs 씩, 거의 같은 상수만큼 내려갔다.** 대기(경합)를 없앴다면
상위 분위가 더 크게 내려간다. 모든 분위가 같은 양만큼 내려간 것은 **요청마다 무조건 붙던
고정 비용**이 빠졌다는 뜻이다. `max` 가 그대로인 것도 같은 이야기다(그건 GC 쪽이라 무관).

**§19.7 에 "미확정" 으로 남겨 둔 추론이 여기서 확인됐다** — auto-commit 기본값 때문에
Hibernate 가 트랜잭션 시작 시점에 커넥션을 잡는다. **DB 를 한 줄도 안 읽는 12만 건이
요청당 500µs 를 쓰고 있었다.**

다만 500µs 는 풀 체크아웃(수십 µs)만으로는 설명이 안 되고, 경합도 아니다
(4,142/s × 500µs = 동시 2건, 풀은 50). 남는 설명은 **MySQL 과 실제로 왕복했다**는 것이다.

```
트랜잭션 시작   →  SET autocommit=0    (왕복 1)
SoldOutException →  rollback            (왕복 2)
트랜잭션 종료   →  SET autocommit=1    (왕복 3)
```

> **이 마지막 단계(왕복 3회)는 산수로 좁힌 것이지 계측한 것이 아니다.**
> 확인하려면 `@Transactional` 을 되돌린 이미지와 지금 이미지에서 라운드 전후로
> `SHOW GLOBAL STATUS LIKE 'Com_rollback'` / `'Com_set_option'` 을 재면 된다 — 12만 vs 0 이 나와야 한다.

### 22.6 매진 요청 1건의 원가 분해

세 측정이 같은 조건이라 그대로 쪼개진다.

| 구성 | 비용 | 비중 |
|---|---:|---:|
| Redis 왕복 2회 (정책 캐시 + `issue.lua`) | 566µs | 40% |
| **`@Transactional` (아무것도 안 지키는)** | **500µs** | **36%** |
| Tomcat + Caffeine + 예외 → `ProblemDetail` | 334µs | 24% |
| **합 = `swr-4.3` med** | **1.40ms** | |

**전체 1.40ms → 334µs, 4.2배.** 그런데 이 단계에서 제일 큰 한 덩어리를 없앤 것은
캐시가 아니라 **애노테이션 한 줄**이었다.

교차 검증이 되는 자리도 있다. 같은 `swr-4.3` 인데 policy 시나리오는 med 1.11ms,
sellout 은 1.40ms 다. policy 는 `NotStarted` 로 `tryIssue` 앞에서 잘려 왕복이 하나 적다 —
**차이 0.29ms 가 Redis 왕복 1회의 값**이고, 위 표의 566µs 와 맞는다.

### 22.7 그리고 그건 캐시 작업이 끝나기 전까지 안 보였다

`@Transactional` 은 처음부터 거기 있었다. 4-0 에서는 100ms 로더와 커넥션 풀 포화(ρ=1.0)에,
4-1~4-3 에서는 Redis 왕복에 묻혀 있었다. **앞의 것들을 다 걷어내고 나서야 36% 짜리로 드러났다.**

§16(`kafka-nocount`)과 같은 모양이다 — 병목을 하나 없애면 다음 것이 보인다.
다른 점은 그때는 "옮겨도 없어지지 않는 경합" 이었고, 이번엔 **애초에 필요 없던 일**이었다는 것이다.
`issue` 는 DB 쓰기가 없고(Kafka 워커가 한다) 읽기는 캐시 로더 안의 `findById` 하나뿐인데
그건 Spring Data 가 자기 트랜잭션을 연다. **바깥 트랜잭션은 처음부터 아무것도 안 지키고 있었다.**

같은 이유로 `swr-4.3` 이 이 시나리오에서 한 일도 전부 헛일이었다 — 캐시 히트 120,001회,
DB 조회 49회, 백그라운드 갱신 48회로 읽어온 정책은 `issue.lua` 가 `0` 을 주는 순간 버려진다.
§18.1 에서 이 트랙을 판 이유("같은 결과를 내는 데 드는 일의 양")가 여기서 제일 노골적이다.

### 22.8 읽을 때 주의

- **`l1cache` 태그는 `@Transactional` 이 **없는** 최종 상태다.** 22.5 의 "있음" 열은
  개발 중 한 변수 실험의 값이고 그 이미지는 남기지 않았다(같은 태그로 덮어 다시 빌드했다).
  되살리려면 애노테이션 한 줄을 되돌려 **다른 태그로** 빌드한다.
- **`swr-4.3` 의 `couponDbReads` 는 부하와 무관하다.** policy(500/s)에서 49,
  sellout(4,000/s)에서도 49 다. §21.4 의 모델대로 갱신 주기를 `fresh-ms` 가 잡으므로
  조회 수는 요청 수가 아니라 시간에만 의존한다. **single-flight 가 산 것은 배수가 아니라
  부하 독립성이었다** — single-flight 가 없는 `rediscache-4-1` 이었다면 이 rate 에서
  약 10,000건이 됐을 것이다(4,000/s × 0.1s × 25 사이클, 미측정 추정).
- **§21.4 의 불변식이 8배 부하에서도 정확히 맞는다.** `49 + 120,001 = 120,050`,
  요청 120,002, 초과 48 = STALE_REFRESH 횟수. policy 라운드의 48 과 같은 값이다.
- `swr-4.3` 의 **워밍업**은 `p(99)<100` 을 깼다(143.66ms). steady 는 7.21ms 로 통과.
  버리는 라운드에서 깨진 것이고 checks 는 100% 였다. steady 의 `max 136.1ms` 는
  라운드마다 `FLUSHALL` 로 정책 캐시가 비워져 첫 요청이 콜드 LOAD 를 타기 때문이다 —
  `100ms(로더) + 20ms(WAIT_BACKOFF_MS) + 오버헤드`, §20.4 의 그 서명이다.
  **`l1cache` 의 max 는 32ms 다.** fast path 가 정책 조회 경로에 안 들어가므로 이 절벽 자체가 없다.
- steady `min = -555ms` 는 §13.2·§18.4 의 음수 샘플(원인 미확정, 12만 샘플 중 하나라 무해).

### 22.9 남은 것

- **`fast-path-ttl-ms` 는 러너와 얽혀 있다.** `reset.ps1` 의 `FLUSHALL` 은 Redis 만 비우고
  **Caffeine L1 은 JVM 안이라 라운드를 건너 살아남는다.** 지금은 리셋~k6 사이가 1초보다
  훨씬 길어 무사하지만, 이 값을 올리면 이전 라운드의 `true` 가 남아 매진 루프 100건이
  전부 409 로 튕긴다. **지금 값에 의존하고 있다.**
- L1 의 stale 은 **한 방향뿐이라 안전하다.** 플래그를 아직 모르면(stale false) 느린 길로 가서
  `issue.lua` 가 `0` 을 주므로 답은 맞다. 반대(stale true)는 재고가 다시 늘어야 틀리는데,
  **되돌리는 경로를 제거해서 재고가 단조 감소**다. 보상을 되살린다면 `restore.lua` 가
  `sold_out` 플래그까지 지워야 하는 이유가 여기다([`architecture.md` §4](architecture.md)).
