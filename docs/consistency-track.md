# 정합성(consistency) 트랙 — 대사 검증과 밟은 함정들

2026-08-18 기록. 대상 이미지 `coupon-service:reconcile-v3`.

측정 트랙(정확성·응답시간·효율)과 달리 이 트랙은 **숫자를 재지 않는다.** PASS/FAIL 만 낸다.
그래서 `docs/load-test-*.md` 의 절 번호 체계에 들어가지 않고 이 문서가 따로 있다.

러너는 `scripts/consistency/windows/run-v2.ps1` 이다.
(`run.ps1` 은 강의 스크립트 개정 **전** 판본의 포팅이라 보존용으로만 남아 있다 — §3.1 참고.)

---

## 1. 무엇을 검증하는가

대사(reconcile)는 Redis 와 DB 가 어긋났을 때 **고칠 수 있는 것만 고치고, 나머지는 알람만 낸다.**
그 경계가 제대로 그어져 있는지가 이 트랙의 주제다.

| | 상황 | 기대 동작 |
|---|---|---|
| Redis 명단 누락 | DB 엔 발급 기록이 있는데 `coupon:{id}:users` 가 비었다 | **자동 보정** (SADD 로 복구) |
| DB 측 불일치 | Redis 만 발급된 상태고 DB 는 모른다 | **알람만.** 아무것도 안 건드린다 |

두 번째가 왜 알람만이냐면 — DB 에 없는 발급을 대사가 마음대로 만들어 내면 그건 복구가 아니라
**과발급**이다. `CouponReconciler.kt:32-34` 의 early return 이 그 경계다.

## 2. 검증 항목 (16개)

### 2.1 실측 확인됨 (9개, `reconcile-v3` 에서 통과)

| 블록 | 항목 | 실측값 |
|---|---|---|
| ① 최근 대사 대상 등록 | 발급 쿠폰을 최근 대사 대상으로 등록 | PASS |
| ② Redis users 누락 자동 보정 | 발급자 명단 복구 | `10` |
| | 자동 보정 횟수 | `1` |
| ③ DB 측 불일치는 알람만 | DB 측 불일치 감지 | `10` |
| | Redis 재고 유지 | `4990` |
| ④ 주기 대사가 스스로 보정 | 발급이 DB 에 기록됨 | `1` |
| | 최근 대사 대상 ZSET 에 등록 | `score=1786978839245` |
| | 명단을 일부러 날림 | `0` |
| | 주기 대사가 명단을 스스로 복구 | `1` |

숫자가 코드 계산과 정확히 맞는다.

- ② `dbDrift = 5000 − (10 + 4990) = 0` → DB 는 정합 → early return 안 함 →
  `userDrift = 5000 − (0 + 4990) = 10`, DB 발급자 10명 전원이 누락이라 안전하게 복구 가능 →
  SADD 후 `autoFixed = 1`. **`1` 은 "10명 보정" 이 아니라 보정 동작 1회다.**
- ③ `dbDrift = 5000 − (0 + 4990) = 10 ≠ 0` → 알람만. 재고 4990 그대로.
- ④ `SREM` 직후 `SCARD = 0` 을 확인했고, 그 뒤 **아무도 `/admin/reconcile/run` 을 부르지 않았는데**
  `SCARD = 1` 이 됐다. 대사를 부르는 곳은 그 엔드포인트와 스케줄러뿐이므로
  `Reconciler.scheduledRecent` 가 한 것이 확정된다.

## 3. 밟은 함정

### 3.1 (핵심) 강의 스크립트가 조용히 개정돼 있었다

**증상.** 러너가 시작하자마자 멈춘다.

```
단계 감지: 소스=part-5-2, 런타임=part-5-1
!! 현재 소스는 part-5-2 인데 떠 있는 coupon-service 는 part-5-1 입니다.
   ... .\build-and-run.ps1 -Tag <태그> 로 빌드해서 띄우세요
```

**시키는 대로 몇 번을 다시 빌드해도 똑같이 멈춘다.** 안내가 원인을 잘못 짚었기 때문이다.

**원인.** 단계를 두 곳에서 **서로 다른 기준으로** 읽고 비교한다.

| | 기준 |
|---|---|
| 소스 감지 | `batch/Reconciler.kt` **파일이 있나** |
| 런타임 감지 | `GET /metrics/reconcile` 이 **응답하나** |

파일은 먼저 생기고 엔드포인트는 나중에 생긴다. 그래서 **한 단계를 다 쓰기 전까지는 이 둘이
반드시 어긋난다.** 강의를 따라가며 단계를 쪼개 구현하는 동안에는 예외가 아니라 항상 지나가는
구간이다.

그런데 진짜 원인은 그 위에 있었다 — **강의 저장소의 `run.sh` 가 이미 개정돼 있었고,
우리가 포팅해 둔 것은 개정 전 판본이었다.**

| | 개정 전 | 개정 후 |
|---|---|---|
| 대사 결과를 읽는 곳 | `GET /metrics/reconcile` 의 누적 카운터 | `POST /admin/reconcile/run` 의 **응답** |
| 리셋 | `POST /metrics/reconcile/reset` | 없음 (한 회차 결과라 리셋할 게 없다) |
| 런타임 감지 | `GET /metrics/reconcile` 이 200 인가 | `GET /admin/reconcile/run` 이 **405** 인가 |

405 를 보는 것이 요점이다. 이 엔드포인트는 POST 전용이라 GET 하면 405 가 오고,
**그 405 자체가 라우트 존재의 증거**다. 그리고 이 라우트는 `Reconciler.kt` 와 같은 시점에
생기므로 소스 감지와 런타임 감지가 같이 참이 된다 — 어긋날 구간 자체가 사라졌다.

**해결.** 개정판을 `run-v2.ps1` 로 새로 포팅했다. `/metrics/reconcile` 은 **만들지 않았다** —
개정판이 더 이상 안 쓴다.

**여기서 배운 것.**

- **포팅본은 원본이 바뀌어도 따라 바뀌지 않는다.** `git status` 에 `scripts/consistency/run.sh` 가
  ` M` 으로 뜨면 그건 "내가 고쳤다" 가 아니라 **"강의가 고쳤다"** 일 수 있다. 포팅본과 대조부터.
- **하네스가 원인을 단정하면 의심한다.** "이미지를 안 만들었다" 는 여러 원인 중 하나일 뿐인데
  메시지는 그것만 말했다. 시키는 대로 해도 안 고쳐지면 메시지를 믿지 말 것.
- mac 원본 `run.sh` 는 CLAUDE.md 규칙상 수정하지 않는다. 그래서 `source_stage` 가
  `com/apiece/coupon/...` 를 보는 채로 남아 있고 — 이 저장소 패키지는 `com/example` 이라 —
  **bash 판은 항상 `part-5-0` 을 뱉는다.** Windows 판만 경로를 고쳐 쓴다.

### 3.2 대사가 DB 불일치를 구조적으로 못 잡고 있었다

**증상.** `FAIL DB 측 불일치 감지 (실제 0, 기대 10)`. 값이 `0` 으로 **오기는** 하니 배선은 정상이다.

**원인.** `IssuedQuantitySynchronizer` 가 `issued_quantity` 를 Redis 재고에서 파생시킨다.

```kotlin
issued = totalQuantity − stock        // 동기화기
dbDrift = totalQuantity − (issued + stock)   // 대사
        = total − (total − stock) − stock = 0
```

**항상 정확히 0 이다.** 같은 열을 정확성 트랙은 "Redis 가 센 발급 수" 로,
대사는 "DB 가 아는 발급 수" 로 읽는다. 뜻이 반대다.

하필 이때 터진 이유 — part-5-2 를 하려고 `@EnableScheduling` 을 켰는데, 그게 `Reconciler` 만
깨운 게 아니라 **그동안 잠자던 동기화기까지 같이 깨웠다.**

**해결.** 지우지 않고 **검증 동안만 껐다.** 동기화 주기를 property 로 뺐다
(`coupon.sync.interval-ms` / `COUPON_SYNC_INTERVAL_MS`, 기본 `1000`).

지우면 안 되는 이유: `CouponRepository.incrementIssueQuantity` 는 호출자가 없으므로
(그 파일 주석이 직접 밝혀 둔다) 동기화기가 이 열의 **유일한 기록자**다. 없애면
`issued_quantity` 가 영원히 0 이 되어 정확성 트랙의 `count_match` 가 영구 FAIL 이 된다.

자세한 것은 [`architecture.md`](architecture.md) §2 의 함정 절.

### 3.3 `docker load` 가 아무 메시지 없이 멈춘다

**증상.** `==> Docker 에 이미지 로드` 에서 무한 대기. 에러도 진행 표시도 없다.
그런데 `docker images` / `docker system df` 같은 다른 명령은 즉답한다.

**원인.** 앞서 `docker load` 를 중간에 끊으면 containerd 가 **콘텐츠 저장소의 레이어 락을
쥔 채로 남는다.** 같은 소스로 만든 다른 태그는 레이어 다이제스트가 같으므로 그 잠긴 ref 를
다시 쓰려다 무한 재시도에 빠진다.

**확인 방법.** `%LOCALAPPDATA%\Docker\log\vm\init.log` 에서 `locked for` 를 찾는다.

```
ref moby/1/tar-617772c7....tar.gz  locked for 13m40s (since 2026-08-17 13:22:03 UTC)
"msg":"(*service).Write failed"
```

**잠긴 시각이 곧 원인이 된 실행이다.** 보조 증거 — `docker load` 프로세스의 누적 CPU 가
0.05초에서 안 늘고, VM 디스크(`docker_data.vhdx`)도 안 커진다.

**해결.** Ctrl+C 후 **Docker 엔진 재시작.** 락은 메모리에 있어 엔진이 다시 뜨면 사라진다.
`docker system prune` 류로는 안 풀린다.

**교훈: `docker load` 중에는 Ctrl+C 하지 않는다.** 태그를 잘못 골랐어도 끝까지 두고
나중에 `docker rmi` 로 지우는 편이 싸다.

### 3.4 새로 만든 `.ps1` 이 파싱 에러를 낸다

**증상.** `문자열에 ' 종결자가 없습니다` 같은 에러가 엉뚱한 줄 번호로 뜬다.

**원인.** 이 저장소의 `.ps1` 은 전부 **UTF-8 BOM** 으로 저장돼 있다. BOM 이 없으면
PowerShell 5.1 이 파일을 CP949 로 읽어서 한글이 깨지고, 깨진 바이트가 따옴표로 오인된다.

**확인.** `head -c 3 <파일>` 이 `ef bb bf` 여야 한다.
`.gitattributes` 는 `*.ps1 text eol=crlf` 도 요구한다.

## 4. 증상 → 무엇부터 의심할까

| 증상 | 먼저 의심 | 확인 |
|---|---|---|
| 하네스가 "이미지를 안 만들었다" 며 멈춤. **다시 빌드해도 그대로** | 강의 스크립트 개정 / 아직 안 만든 엔드포인트 | `git status` 에 원본 `.sh` 가 ` M` 인가. 소스·런타임 감지가 각각 무엇을 보는가 |
| 대사 수치가 `0` 인데 코드는 멀쩡해 보임 | `issued_quantity` 파생 | 그 시점 `COUPON_SYNC_INTERVAL_MS` 가 얼마인가 |
| 검증은 통과하는데 진짜 도는지 미덥다 | `auditAll` 로만 돌고 있는지 | ZSET(`coupon:reconcile:recent`)이 비어도 통과하는가 |
| `docker load` 무응답 | containerd ingest 락 | `init.log` 에서 `locked for` |
| `.ps1` 파싱 에러 (따옴표/중괄호) | BOM 없음 | `head -c 3` 가 `ef bb bf` 인가 |
| 설정을 줬는데 안 먹음 | compose 미선언 | `docker-compose.yml` 의 `environment` 에 그 이름이 있는가. 없으면 셸 변수는 조용히 무시된다 |
| `count_match` 가 영구 FAIL | 동기화기가 안 돎 | `@EnableScheduling` / `COUPON_SYNC_INTERVAL_MS` |

**공통 원칙 하나.** 이 프로젝트에서 값이 **너무 깔끔하게 0** 이면 기능이 꺼져 있거나
계산이 구조적으로 상쇄되고 있을 가능성을 먼저 본다. §3.2 가 정확히 그 경우였다.

## 5. 남은 과제

- **①의 판정이 약하다.** `ZSCORE` 가 "비어 있지 않다" 만 본다. score 가 발급 시각인지,
  `scheduledRecent` 의 창에 실제로 걸리는지는 ④가 간접적으로만 보여 준다.
- **`autoFixed` 가 뭉쳐 있다.** 매진 플래그 보정과 명단 보정이 한 숫자다. `2` 가 나오면
  무엇을 고쳤는지 모른다.
- **early return 이 명단 누락을 가린다.** DB 가 어긋난 쿠폰은 Redis 명단도 비어 있으면
  사람이 DB 를 손볼 때까지 **그것도 영영 안 고쳐진다.** 의도된 보수성이지만 지금은
  로그 한 줄로만 남는다.
- ⑤(워터마크)를 포함한 16개 전체 실행 결과는 아직 안 남겼다.
