## 13. 응답시간 트랙 — 큐 디커플링 (2026-08-14)

### 13.1 왜 트랙을 따로 만들었나

12절까지의 관심사는 **정확성**(과발급·중복발급)이었고, 응답시간은 부산물로 곁눈질했다.
큐 디커플링부터는 관심사가 **사용자 응답 지연 분포(P99)** 그 자체다. 재는 것이 다르면
시나리오도 검증도 달라야 해서 스크립트를 두 트랙으로 나눴다.

| 트랙 | 스크립트 | 재는 것 |
|---|---|---|
| 정확성 | `scripts/concurrency/windows/load-test.ps1` | 과발급·중복발급, 카운터 일치 |
| 응답시간 | `scripts/response/windows/run.ps1` | `issue_latency` 분포, 부하 전달률 |

부하 조건은 **양쪽이 같다** (`constant-arrival-rate` 5,000/s × 30s, USER_POOL 20,000, 재고 5,000).
그래야 12절까지의 기록과 이어서 읽을 수 있다.

응답시간 트랙에만 있는 두 가지:

- **워밍업 라운드.** 1회차는 버리고 2회차를 쓴다. JIT·Hikari 풀·Lettuce 커넥션이 데워지는
  비용이 1회차 응답시간에 그대로 섞이기 때문이다. 실제로 차이가 컸다 — 13.2 참고
- **드레인 폴링.** k6 이 끝나도 쓰기가 끝난 것이 아니다. `issuance` 행 수가 멈출 때까지
  기다린 뒤에 검증한다. 큐 구현에서 이것이 없으면 아직 안 들어온 행을 세게 된다

### 13.2 `status 0` 을 지연 분포에서 뺐다

연결이 거부되면 k6 의 `res.timings.duration` 이 0ms 에 가깝게 기록된다. 그대로 두면
**"아주 빠른 응답" 이 대량으로 섞여 p99 가 실제보다 좋게 나온다.** 12.7.3 시점에는 요청의
15~27% 가 여기 해당했으니, 그 상태로 p99 를 읽었다면 완전히 틀린 값을 봤을 것이다.

그래서 `issue_burst.js` 는 `status 0` 을 `issue_latency` 에 넣지 않고 `status_conn_error`
카운터로 따로 센다. **여기서 말하는 p99 는 "앱이 실제로 응답한 요청의 p99"** 이고,
`status_conn_error` 가 크면 그만큼 살아남은 요청만 본 수치라는 뜻이므로 같이 읽어야 한다.

**threshold 판정은 k6 의 종료 코드로 하지 않는다.** `queue-mem` 실행이 p(99)=5.62ms,
**최댓값 46.59ms** 로 어떤 시점에도 500ms 를 넘길 수 없는데 `thresholds have been crossed` 를
찍고 exit 99 로 끝난 적이 있다. **원인은 모른다.** `issue_latency` 의 `min` 이 음수로 찍히는 것
(컨테이너 클럭 문제로 보인다)을 의심했지만 아니었다 — 음수가 섞였는데 exit 0 인 실행도 있다.

요약 JSON 의 `metrics.issue_latency.thresholds` 가 실제 판정이다 (`true` = 넘김, `false` = 통과).
`run.ps1` 이 그것을 읽어 출력하고, 종료 코드와 어긋나면 그 사실을 알린다.

### 13.3 결과

셋 다 본 측정 라운드. `lua-pool` 은 동기 쓰기, 뒤 둘은 큐 뒤로 뺀 쓰기다.

| | `lua-pool` | **`queue-mem`** | `queue-async` |
|---|---:|---:|---:|
| `issue_latency` p(99) | 705ms | **5.62ms** | 5.59ms |
| avg | 27.51ms | 1.40ms | 1.43ms |
| med | 531µs | 1.23ms | 1.25ms |
| 성공 응답 p(99) `{expected_response:true}` | 1.03s | **43.28ms** | 35.80ms |
| `http_reqs` (의도 150,000) | 145,707 | **150,001** | 150,002 |
| `dropped_iterations` | 2,259 | **0** | 0 |
| `vus_max` (상한 5,000) | 3,073 | **2,000** | 2,000 |
| `status_conn_error` | 0 | 0 | 0 |
| checks | 100% | 100% | 100% |
| 정확성 / Redis 재고 | OK / 누수 0 | OK / 누수 0 | OK / 누수 0 |

`queue-async` 는 직접 만든 큐·워커를 Spring `ApplicationEventPublisher` + `@Async` 로 바꾼 것인데
**수치가 사실상 같다.** 풀 설정이 `corePoolSize=1, queueCapacity=10_000` 이라 앞 구현과 특성이
동일하기 때문이다 — 단일 컨슈머, 용량 10,000. 쓰기 드레인도 초당 약 155행으로 같다.
**프레임워크로 갈아끼운 것은 코드가 줄어든 것이지 성능이 달라진 것이 아니다.**
병목이 큐가 아니라 그 뒤에 있다는 13.5 의 진단이 이것으로 한 번 더 확인된다.

이하 서술은 `lua-pool` → `queue-mem` 비교를 기준으로 한다 (`queue-async` 도 같은 결론이다).

**p99 가 125배 낮아졌다.** 그리고 이 표에서 더 중요한 것은 아래 두 줄이다.

**부하가 처음으로 100% 전달됐다.** `dropped_iterations` 가 0 이고 `vus_max` 가
`preAllocatedVUs` 2,000 에서 늘지도 않았다 — VU 가 대기에 묶이지 않았다는 뜻이다.
9절의 신뢰 조건("10% 이하 + `vus_max` 가 상한에 안 붙음")을 여유 있게 만족한다.
5절에서 "튜닝으로 안 없어진다" 고 했던 `dropped_iterations` 는 **앱이 빨라지자 사라졌다.**

**워밍업 라운드가 값을 했다.** 같은 실행의 1회차 p99 는 102.93ms, 2회차는 5.61ms 다.
18배 차이라, 워밍업 없이 쟀다면 개선폭을 크게 과소평가했을 것이다.

### 13.4 median 은 오히려 올라갔다 — 게이트가 DB 뒤로 돌아왔다

531µs → 1.23ms. p99 개선에 묻혀 안 보이지만 이유가 분명하다.

`CouponService.issue` 에 `@Transactional` 이 다시 붙고 `couponRepository.findById` 가
**Redis 게이트보다 앞에서** 돈다. 즉 409 로 튕길 145,000건도 전부 Hikari 커넥션을 잡고
`SELECT` 를 한 번씩 친다. 12.3 에서 게이트를 DB 앞으로 옮겼던 것을 되돌린 셈이다.

요청당 약 700µs. 지금은 큐 덕분에 여유가 있어 문제가 안 되지만,
**12.3 이 "거절 경로는 병목이 아니다" 라고 결론 낸 것과 같은 이유로 이득도 없다.**

### 13.5 쓰기 처리량은 크게 떨어졌다

드레인 폴링 로그가 그대로 보여준다 (본 측정 라운드).

```
k6 종료 시점    issuance rows: 3,815      ← 30초 동안 3,815행
  +1s                          3,966
  +5s                          4,433
  +9s                          5,000      ← 초당 약 155행
```

전에는 5,000행이 부하 구간 안에 다 들어갔다. 지금은 **k6 이 끝나고도 9초를 더 쓴다.**
사용자는 200 OK 를 받았지만 그 발급이 DB 에 앉는 것은 9초 뒤다.

원인은 워커 쪽에 다 있다.

- 워커가 **단일 스레드**다 (`InMemoryIssuanceWorker` 의 `thread(name="issuance-worker")` 하나)
- 이벤트마다 트랜잭션을 열어 `INSERT issuance` + `incrementIssueQuantity` 를 한다.
  뒤엣것이 **`coupon` 단일 행 UPDATE** — 12.4 에서 처리량을 10배 올린 그 변경이
  핫패스에서 뺐던 바로 그 쿼리다. 워커가 단일 스레드라 요청끼리 직렬화되지는 않지만,
  1초 주기 `IssuedQuantitySynchronizer` 가 같은 행을 덮어쓰며 부딪친다

이벤트당 약 6.5ms 가 나오는 계산이다.

**그래서 이 실험의 결론은 "큐가 병목을 없앴다" 가 아니라 "병목을 사용자 응답 밖으로 옮겼다" 다.**
목적이 그것이었으니 성공이지만, 없앤 것과 옮긴 것은 다르다.

### 13.6 남은 한계

- **인메모리 큐라 프로세스가 죽으면 큐에 남은 이벤트가 사라진다.** Redis 재고는 이미 차감된
  뒤이므로 그만큼 과소발급이 된다. 측정 중에 `docker compose restart coupon-service` 를
  하면 안 되는 이유다
- **보상 로직이 없어졌다.** 예전 `CouponService` 는 DB 쓰기 실패 시 `couponIssuer.restore` 로
  Redis 재고를 되돌렸는데, 지금은 워커가 예외를 로그만 찍고 이벤트를 버린다.
  12.2 에서 잡았던 재고 누수가 다시 생길 수 있는 경로다
  (이번 두 라운드에서는 누수 0 이었다. 잡히지 않았을 뿐 막혀 있는 것은 아니다)
- **`count_match` 의 의미가 또 바뀌었다.** `issued_quantity` 를 두 writer 가 건드린다 —
  워커의 상대적 `+1` 과 동기화기의 절대 덮어쓰기. 지금은 드레인 후 둘 다 5,000 으로 수렴해
  OK 가 나오지만, 이 열이 잡아주는 것은 더 이상 없다고 봐야 한다
- **`queue-mem` 의 p99 5.61ms 가 앱의 상한인지는 모른다.** 부하 상한(5,000rps)에 먼저 걸렸다.
  더 세게 걸어야 알 수 있다 — 그런데 그러면 12절까지의 기록과 비교가 깨진다

## 14. 메시징 기반 교체 — Kafka (2026-08-14)

### 14.1 무엇을 바꿨나

큐만 갈아끼웠다. 게이트(Redis Lua)도, 쓰기 트랜잭션도 그대로다.

| | `queue-async` | `kafka` |
|---|---|---|
| 큐 | `ApplicationEventPublisher` + `@Async` | Kafka 토픽 `issuance.requested` (파티션 3) |
| 큐의 위치 | JVM 힙 (`ThreadPoolTaskExecutor`, 용량 10,000) | 브로커 디스크 |
| 소비자 | 전용 스레드 1개 | `@KafkaListener(concurrency = 3)` — 컨슈머 3개 |
| 분배 키 | 없음 | `userId` (같은 사용자는 한 파티션에서 순서대로) |
| 실패 처리 | 없음 (로그만) | `DefaultErrorHandler` 1초 × 3회 → `issuance.requested.DLT` |

compose 에 `apache/kafka:3.8.0` 을 KRaft 모드로 띄운다 (ZooKeeper 컨테이너가 없다).

**바뀐 것이 둘이라는 점을 먼저 밝혀 둔다** — 메시징 기반(인프로세스 → Kafka)과
소비자 병렬도(1 → 3)를 한 태그에서 같이 바꿨다. 14.5 의 결론이 이 사실에 기대지 않는
이유는 거기서 따로 적는다.

### 14.2 결과

본 측정 라운드. 부하 조건은 12절부터 동일하다
(`constant-arrival-rate` 5,000/s × 30s, USER_POOL 20,000, 재고 5,000).

| | `queue-mem` | `queue-async` | **`kafka`** |
|---|---:|---:|---:|
| `issue_latency` p(99) | 5.62ms | 5.59ms | **5.95ms** |
| avg | 1.40ms | 1.43ms | 1.52ms |
| med | 1.23ms | 1.25ms | 1.35ms |
| 성공 응답 p(99) `{expected_response:true}` | 43.28ms | 35.80ms | 37.8ms |
| `http_reqs` (의도 150,000) | 150,001 | 150,002 | 150,000 |
| `dropped_iterations` | 0 | 0 | 0 |
| `vus_max` (상한 5,000) | 2,000 | 2,000 | 2,000 (실측 max 196) |
| `status_conn_error` | 0 | 0 | 0 |
| checks | 100% | 100% | 100% |
| 정확성 / Redis 재고 | OK / 누수 0 | OK / 누수 0 | OK / 누수 0 |
| 쓰기 드레인 | ~155/틱 | ~155/틱 | **~157/틱** |
| 소비자 병렬도 | 1 | 1 | **3** |

**"행/초" 가 아니라 "행/틱" 이라고 쓴 이유.** `verify-burst.ps1` 은 `Start-Sleep -Seconds 1`
뒤에 `docker compose exec mysql` 로 세는데, exec 왕복 시간이 표본 간격에 얹힌다. 실제 간격은
1초보다 길고 진짜 초당 처리량은 이 숫자보다 **낮다.** 13.5 의 155 도 같은 방법으로 잰 값이라
**구현끼리의 비교는 그대로 성립한다.** 절대값이 필요해지면 하네스를 먼저 고쳐야 한다 (16.6).

### 14.3 응답시간은 사실상 그대로다

med 1.25 → 1.35ms, p99 5.59 → 5.95ms. **10% 이내라 과독하면 안 된다.**
굳이 읽자면 요청 경로에 JSON 직렬화와 프로듀서 accumulator append 가 들어온 값인데,
그 정도 크기다.

**인프로세스 큐를 브로커로 바꾼 비용이 사용자 응답에는 거의 없다.** `send` 가 비동기라
요청 스레드는 레코드를 버퍼에 넣고 바로 돌아온다 — 인메모리 큐에 `offer` 하던 것과
구조적으로 같은 일이다.

### 14.4 대신 콜드스타트 비용이 커졌다

| | 워밍업 p(99) | 워밍업 성공 응답 med |
|---|---:|---:|
| `queue-mem` | 102.93ms | — |
| `kafka` | **190.55ms** | **161.79ms** |

1.85배다. 이유가 분명하다 — **성공 5,000건은 전부 첫 1초에 몰린다**(재고 5,000, 도착 5,000/s).
그 1초가 프로듀서가 메타데이터와 파티션 리더를 처음 조회하는 시점과 정확히 겹친다.
JIT 뿐이던 워밍업 비용에 브로커 핸드셰이크가 얹힌 것이다.

**워밍업 라운드를 버리는 설계가 더 중요해졌다.** 이걸 안 버리고 쟀다면 p99 가 32배 나쁘게 나온다.

### 14.5 컨슈머를 3배로 늘렸는데 쓰기 처리량이 안 움직였다

이번 라운드의 결론이다. 155 → 157, 1.3% 는 노이즈다.

본 측정 드레인 폴링의 틱당 증가분:

```
158, 156, 156, 158, 155, 158, 157   → 평균 156.9, 편차 ±0.8%
```

"병렬도를 올렸는데 안 올랐다" 는 주장은 병렬도가 진짜였는지부터 의심해야 하므로,
근거를 셋 모아 둔다.

**(1) 파티션 쏠림이 아니다.** 브로커에서 직접 확인한 종료 오프셋 (워밍업 5,000 + 본 측정 5,000):

```
issuance.requested:0 = 3,361   consumer-1   lag 0
issuance.requested:1 = 3,354   consumer-2   lag 0
issuance.requested:2 = 3,285   consumer-3   lag 0
```

33.6 / 33.5 / 32.9%. `userId` 해시가 고르게 갈랐고 컨슈머 셋이 하나씩 물었다.

**(2) 쓰기 경로는 JIT 에 반응하지 않는다.** 같은 실행의 워밍업 드레인이 158.75/틱,
본 측정이 156.9/틱으로 **사실상 같다.** 그런데 같은 두 라운드의 응답 p99 는 190.55 → 5.95ms 로
32배 차이가 난다. **응답 경로는 데워지는데 쓰기 경로만 안 데워진다 = CPU 를 쓰는 것이 아니라
무언가를 기다리고 있다.**

**(3) Kafka 가 못 따라간 것도 아니다.** 드레인 첫 표본이 이미 3,878행이고 그 뒤로 증가분이
일정하다. 컨슈머는 밀린 메시지를 앞에 쌓아 두고 일정한 속도로 비우고 있었다 — 브로커가 아니라
컨슈머 뒤가 상한이라는 전형적인 모양이다.

**그래서 13.5 가 남긴 질문의 절반이 닫힌다: "워커가 하나여서" 가 아니다.**
행당 6.37ms 인데, 컨슈머 셋이 전부 `coupon` 단일 행의 X 락을 잡으려 줄 서고 그 락을
커밋(fsync)까지 쥐고 있으면 실효 병렬도가 1 이 되고 그룹 커밋도 못 탄다. 그 그림과 맞는다.

### 14.6 그 `coupon` 행 UPDATE 는 아무 일도 안 하고 있다

`IssuanceTransactionWriter.insertAndIncrement` 는 INSERT 뒤에 `incrementIssueQuantity`
(= `issued_quantity = issued_quantity + 1`) 를 친다. 그런데 `IssuedQuantitySynchronizer` 가
1초마다 `total_quantity − (Redis 재고)` 로 **절대값 덮어쓰기**를 한다.

**워커가 올린 값은 1초 안에 지워진다. 결과에 기여하지 않는다.**
드레인 중에는 Redis 재고가 이미 0 이므로 동기화기가 매초 5,000 을 써 넣고, 워커들이 그 위에
+1 씩 얹었다가 다음 초에 다시 5,000 으로 눌린다. 마지막에 동기화기가 이겨서 `count_match` 가
OK 로 보일 뿐이다.

즉 이 쿼리는 **결과에 기여하지 않으면서 컨슈머 셋을 한 줄로 세우는 일만 한다.**
12.4 에서 핫패스에서 빼내 처리량을 10배로 만든 바로 그 쿼리가, 워커 안으로 자리만 옮겨
같은 짓을 반복하고 있다. 게다가 1초 주기 동기화기가 같은 행을 두고 워커와 부딪친다.

**다음 실험은 여기서 나온다** — 이 한 줄만 빼고 다시 잰다. 오르면 병목은 `coupon` 단일 행
UPDATE 로 확정되고, 안 오르면 커밋당 fsync 가 상한이라 다음 레버는 배치다.

### 14.7 Kafka 로 옮기며 새로 생긴 실패 모드

**발급 한 장이 조용히 사라지는 경로가 생겼다.** `CouponService.issue` 는
`couponIssuer.tryIssue` 로 Redis 재고를 깎은 다음 `kafkaTemplate.send(...)` 를 부르고
**그 결과를 버렸다.** send 가 실패하면 사용자는 200 OK 를 받았는데 그 한 장은 아무에게도 가지
않고, 그 사용자는 `coupon:{id}:users` 에 남아 다시 시도해도 영영 거절된다.
`acks=1` + 브로커 1대라 ack 을 받고도 유실될 수 있다.

**DB 안에는 아무 모순이 없어 `verify` 의 세 판정은 전부 OK 로 통과한다** —
12.2 에서 23장을 놓쳤던 그 실패 모드와 같다. 인프로세스(`@Async`) 시절에는 실패가 예외로
드러났으니, 큐를 프로세스 밖으로 내보내면서 새로 생긴 구멍이다.

되돌리는 코드는 있었지만 **불러도 틀렸다.** `CouponIssuer.restore` 가
`coupon:{id}:issued` 에서 SREM 했는데 `issue.lua` 가 SADD 하는 곳은 `coupon:{id}:users` 다.
그대로 호출부만 붙였으면 재고만 돌아오고 사용자는 계속 차단된 채 남았을 것이다.
`kafka-restore` 에서 고쳤다 — 15절.

그밖에 같이 적어 둘 것:

- **재시도 1초 × 3회는 그 파티션을 통째로 멈춘다.** 순서를 보장하려면 실패한 레코드를
  넘어갈 수 없다. 실패가 하나 나면 드레인이 그만큼 주저앉는다
  (**17.5 에서 실측으로 확인됐다** — 같은 파티션의 두 번째 건이 3.5초 뒤에야 처리됐다)
- **파티션이 3개로 고정이다.** 컨슈머를 4 이상으로 올려도 하나는 논다.
  (`kafka` ~ `kafka-nocount` 시점에는 이 3이 `KafkaTopicConfig` 가 아니라
  `docker-compose.yml` 의 `KAFKA_NUM_PARTITIONS: 3` 에서 왔다 — 17.1 참고)
- **`reset.ps1` 은 토픽을 비우지 않는다.** 인메모리 큐 시절과 위험의 방향이 뒤집혔다 —
  [`architecture.md` §7](architecture.md) 의 함정 항목 참고

## 15. 사라지는 발급을 막는다 — `kafka-restore` (2026-08-15)

> **이 절의 구현은 4-4 에서 제거됐다 (2026-08-17).** 매진 fast path 가 세우는
> `coupon:{id}:sold_out` 플래그를 `restore.lua` 가 안 지워서, **복구한 재고를 fast path 가
> 도로 막는** 구조가 됐다. 살리는 대신 과소발급을 받아들이기로 했다 —
> 판단과 되살리는 법은 [`architecture.md` §4](architecture.md).
> **아래 기록은 그대로 유효하다.** 어떤 결함이었고 어떻게 막았는지가 남아 있어야
> 되살릴 때 다시 읽을 수 있다.

14.7 의 구멍 하나만 막은 태그다. 성능 실험이 아니라 정확성 수정이다.

### 15.1 무엇을 고쳤나

| 파일 | 고친 것 |
|---|---|
| `lua/restore.lua` (신설) | 되돌리기를 원자적으로. `SREM` 이 실제로 지웠을 때만 `INCR` 한다 |
| `CouponIssuer.restore` | 그 스크립트로 교체. 죽은 `issuedKey`(`coupon:{id}:issued`) 삭제 |
| `IssuanceRequestProducer.publish` | `CompletableFuture<SendResult<..>>` 를 반환한다 (삼키지 않는다) |
| `CouponService.issue` | 실패하면 되돌린다 — 비동기는 `whenComplete`, 동기 예외는 `try/catch` 로 되돌린 뒤 재던짐 |
| `KafkaConfig` | `max.block.ms` 60초 → 3초. `addTrustedPackages` 의 패키지명 오타(`com.apiece`) 수정 |

**`SREM` 성공을 조건으로 `INCR` 하는 것이 핵심이다.** 두 번 불려도 재고가 두 번 늘지 않는다.
프로듀서 콜백은 중복 호출을 막아 주지 않으므로, 이 멱등성이 없으면 보상이 과발급을 만든다.

**`max.block.ms` 를 줄인 이유는 성능이 아니다.** 기본값 60초면 브로커가 죽었을 때 발급 요청마다
Tomcat 스레드가 60초씩 묶여 앱 전체가 같이 멈춘다. 실패는 빨리 드러나야 보상도 빨리 돈다.

**보상 정책은 application 계층에 뒀다.** 프로듀서가 `CouponIssuer` 를 알게 하면
`infrastructure/messaging` 이 발급 정책을 알게 된다. 프로듀서는 future 를 돌려주기만 한다.

### 15.2 어떻게 확인했나 — 정상 실행으로는 증명이 안 된다

send 실패는 건강한 실행에서 나지 않는다. 그래서 **브로커를 일부러 죽이고** 잰다.

```powershell
docker compose stop kafka
# 발급 3건 시도 → max.block.ms=3000 이라 3초쯤 뒤 500
docker compose exec redis redis-cli GET coupon:1:stock    # 5000 (되돌아옴)
docker compose exec redis redis-cli SCARD coupon:1:users  # 0
docker compose start kafka
```

고치기 전(`kafka` 태그)이면 재고 4,997 / `users` 3 이 남는다. **이 대조가 증거다.**
`-Tag kafka -NoBuild` 로 되돌리면 고치기 전 상태를 직접 볼 수 있다.

**실측 (2026-08-15).** 요청 3건 모두 500, 재고 5,000 복구, `SCARD coupon:1:users` = 0.

```
15:09:39.934  TimeoutException: Topic issuance.requested not present in metadata after 3000 ms
15:09:39.950  ERROR CouponService: 발급 요청 발행 실패 — 재고 보상 완료: couponId=1, userId=1
15:09:42.978  ... userId=2
15:09:45.994  ... userId=3
```

**"재고 보상 완료" 라는 문구가 판정의 핵심이다.** `restore.lua` 가 `1` 을 돌려줬을 때만 나오고,
그것은 `SREM` 이 실제로 그 사용자를 지웠다는 뜻이다. 즉 **재고가 깎여 있었고 되돌렸다.**
"애초에 안 깎여서 5,000 이었다"(`tryIssue` 앞에서 죽은 경우)와 구별되지 않으면 이 검증은
아무것도 증명하지 못하는데, 이 한 줄이 그것을 가른다.

실패 간격이 39.93 → 42.97 → 45.99 로 **정확히 3.02초**다. `max.block.ms=3000` 이 그대로 먹었다.
기본값이었으면 요청당 60초였다.

**`LoggingProducerListener` 도 같은 실패를 이미 찍고 있었다.** 즉 `kafka` 태그에서도 로그는
남고 있었는데 재고는 그대로 샜다 — **로그가 남는 것과 처리되는 것은 다르다.**

### 15.2.1 응답시간 회귀는 없다 — 그런데 p99 만 보면 반대로 읽힌다

본 측정 라운드 (2026-08-15).

| steady | `kafka` | `kafka-restore` | |
|---|---:|---:|---|
| med | 1.35ms | **1.25ms** | −7% |
| p(90) | 1.50ms | **1.37ms** | −9% |
| p(95) | 1.59ms | **1.45ms** | −9% |
| avg | 1.52ms | **1.46ms** | −4% |
| **p(99)** | **5.95ms** | **6.45ms** | **+8%** |
| max | 58.2ms | 83.1ms | +43% |
| 실측 `vus` max | 196 | **12** | −94% |
| 쓰기 드레인 | 156.9/틱 | 160.5/틱 | +2% |
| checks / `status_conn_error` / `dropped_iterations` | 100% / 0 / 0 | 100% / 0 / 0 | |
| 정확성 / Redis 재고 | OK / 누수 0 | OK / 누수 0 | |

**p99 하나만 올랐고 나머지는 전부 내려갔다.** 진짜 회귀라면 분포의 몸통도 같이 밀려야 하는데
반대 방향이고, VU 최대치가 196 → 12 로 떨어졌다 — 이번 실행에서 앱이 요청을 **더** 여유 있게
받아냈다는 뜻이다. **단일 실행끼리의 p99 8% 차이는 판정 근거가 못 된다.** 꼬리 노이즈로 읽는다.

예상과 맞는다. `whenComplete` 등록은 성공한 5,000건에만 붙고, 409 로 튕기는 145,001건은
닿지도 않는다.

**워밍업 값은 구현 비교에 쓰면 안 된다는 것이 한 번 더 확인됐다.** 같은 코드인데 워밍업 p99 가
`kafka` 190.55ms → `kafka-restore` 139.5ms, 워밍업 성공 med 가 161.79 → 107.94ms 로 내려갔다.
브로커가 이미 떠 있었고 토픽도 이미 있어서 콜드스타트 경로가 짧아진 것이다.
14.4 의 해석(콜드스타트 비용의 정체는 브로커 핸드셰이크)과 같은 방향이지만, **그만큼
워밍업 수치는 브로커 상태에 흔들린다.**

### 15.3 남는 한계 — 이 보상은 완전하지 않다

**ack 이 애매하게 실패하면 과잉 보상이 된다.** 브로커가 저장은 했는데 ack 이 타임아웃된
경우, 컨슈머는 행을 쓰고 보상은 재고를 되돌린다. 그러면 재고가 총량을 넘어 5,001장이 나갈 수 있다.
중복 행은 `uk_issuance_user_coupon` 이 막지만 **총량 초과는 아무도 못 막는다.**

지금 선택은 **"조용히 사라지는 것보다 드물게 한 장 더 나가는 편이 낫다"** 이고,
이것은 트레이드오프이지 해결이 아니다. 근본 해법은 아웃박스(DB 트랜잭션과 발행을 한 덩어리로)인데
이 단계에서는 과하다고 보고 미뤘다.

**보상 자체가 실패하는 경우도 남는다.** Redis 가 죽어 있으면 되돌릴 수단이 없다.
그때는 ERROR 로그가 유일한 흔적이다.

**비동기 실패 경로는 아직 안 재봤다.** 15.2 는 메타데이터가 없는 상태라 `send` 가 3초 만에
동기로 던졌다. 메타데이터가 캐시된 뒤에 브로커가 죽으면 `send` 는 레코드를 버퍼에 넣고
곧바로 돌아가며, 실패는 `delivery.timeout.ms`(기본 **120초**) 뒤에 콜백으로 온다.
보상은 돌지만 **그 2분 동안 재고는 새어 있는 상태**다. 이 값을 줄일지는 따로 판단한다.

**응답 코드가 틀렸다.** 지금 사용자에게 나가는 것은 `KafkaException` 이 그대로 올라간
맨 500 이고 `GlobalExceptionHandler` 의 sealed 계층을 타지 않아 `code` 도 없다.
그런데 **보상을 했으므로 그 사용자는 지금 재시도하면 성공한다** — 재고도 돌아왔고
`:users` 에서도 빠졌다. 500 은 "재시도해도 소용없다" 로 읽히므로 의미가 반대다.
정직한 응답은 503(재시도 가능)이다.

**브로커가 죽어 있는 동안 요청 하나가 Tomcat 스레드를 3초씩 잡는다.** 200 스레드면
66 req/s 가 상한이 된다. 60초짜리보다 훨씬 낫지만 사라진 문제는 아니다.

## 16. 병목의 정체 — `kafka-nocount` (2026-08-15)

14.6 에서 지목한 한 줄만 뺐다.
`IssuanceTransactionWriter` 의 `couponRepository.incrementIssueQuantity(event.couponId)`.

기능 손실은 없다. `issued_quantity` 는 `IssuedQuantitySynchronizer` 가 1초마다 Redis 재고에서
계산해 절대값으로 덮어쓰므로, 워커의 상대적 `+1` 은 애초에 결과에 기여하지 않고 있었다.
(같은 태그에 15절의 503 응답도 들어갔지만 그것은 `send` 실패 경로에서만 실행돼
측정 중에는 한 번도 타지 않는다.)

### 16.1 드레인이 사라졌다

본 측정·워밍업 두 라운드 모두, `verify-burst.ps1` 의 증가분 줄이 **한 줄도 안 찍혔다.**
이 스크립트는 행 수가 변할 때만 찍으므로, **k6 이 끝난 시점에 이미 5,000행이 다 들어가 있었다**는 뜻이다.

```
kafka-restore   +1s 4028 ... +7s 4991 → +8s 5000     (부하 종료 후 8틱)
kafka-nocount   드레인 완료. issuance rows = 5000    (증가분 줄 없음)
```

### 16.2 그런데 "몇 배 빨라졌다" 고 쓰면 틀린다 — 하네스가 바닥을 쳤다

| | `kafka-restore` | `kafka-nocount` |
|---|---:|---:|
| k6 종료 시점 행 수 | ~3,868 | **5,000 (이미 완료)** |
| 5,000행까지 총 소요 | 30s + 8틱 ≈ 40초 | **≤ 약 31초** |
| 평균 쓰기 속도 | ~125/s | **≥ 약 160/s** |

**하한이 160/s 이고 상한은 모른다.** 부하 구간(30초) 안에서 끝났다는 것만 알 뿐,
t=5초에 끝났는지 t=29초에 끝났는지 구별할 수단이 없다. 개선폭은 **최소 25%, 상한 미상**이다.

**드레인 폴링은 "부하가 끝난 뒤에도 계속 쓰는" 구현을 재려고 만든 도구다.**
그게 아니게 되는 순간 아무것도 못 잰다. 이 태그부터는 **부하 구간 안에서 샘플링**해야 한다
(그리고 그때 13.5·14.2 의 "틱당" 단위 문제도 같이 없앨 수 있다).
**개선폭이 작다는 뜻이 아니라 자가 못 미친다는 뜻이다.**

### 16.3 대신 응답 분포가 통째로 밀렸다 — 이것은 노이즈가 아니다

| steady | `kafka-restore` | `kafka-nocount` | |
|---|---:|---:|---|
| med | 1.25ms | 1.39ms | +11% |
| p(90) | 1.37ms | 1.78ms | +30% |
| p(95) | 1.45ms | 2.30ms | +59% |
| p(99) | 6.45ms | 11.74ms | +82% |
| avg | 1.46ms | 1.80ms | +23% |
| 성공 응답 p(99) | 43.55ms | 62.9ms | +44% |
| checks / `status_conn_error` / `dropped_iterations` | 100% / 0 / 0 | 100% / 0 / 0 | |
| 정확성 / Redis 재고 | OK / 누수 0 | OK / 누수 0 | |

**15.2.1 과 모양이 다르다는 점이 판정의 근거다.** 그때는 p99 만 오르고 med·p90·p95 는
내려가서 꼬리 노이즈로 읽었다. 이번은 med 부터 p99 까지 **한 방향으로 단조롭게** 밀렸다.
이런 모양은 노이즈로 나오지 않는다.

**그리고 이것이 쓰기가 빨라졌다는 간접 증거다.** 전에는 쓰기 일감의 상당 부분이 부하가 끝난
뒤(측정 창 밖)로 밀려나 있었다. 이제 전부 부하 구간 안에서 처리되니 요청 경로의 145,002건
`SELECT` 와 Hikari 커넥션·CPU 를 같이 다툰다. **일이 사라진 것이 아니라 측정 창 안으로 들어왔다.**

### 16.4 결론 — 병목은 `coupon` 단일 행 UPDATE 였다

13.5 에서 열고 14.5 에서 절반을 닫은 질문이 여기서 닫힌다.

| 후보 | 판정 |
|---|---|
| 워커가 하나여서 | **아니다** (14.5 — 컨슈머 3개로 늘려도 155 → 157) |
| `coupon` 단일 행 UPDATE 의 경합 | **맞다** (16.1·16.3) |
| 커밋당 fsync 가 상한 | 아니다 — 그랬다면 이 한 줄을 빼도 아무 변화가 없어야 한다 |

한 줄을 빼자 (a) 부하 종료 후 드레인이 사라졌고 (b) 응답 분포가 밀렸다.
둘 다 **"쓰기가 빨라져 부하 구간 안으로 들어왔다"** 하나로 설명된다.

**12.4 의 교훈이 그대로 반복됐다.** 거기서 핫패스에서 빼내 처리량을 10배로 만든 그 쿼리가,
큐 뒤 워커 안으로 자리를 옮겨 같은 일을 하고 있었다. **경합 지점은 옮겨도 없어지지 않는다.
어디에 있든 단일 행 UPDATE 는 그 경로의 상한이다.**

### 16.5 `count_match` 가 되살아났고, 통과했다

`issued_quantity` 를 이제 `IssuedQuantitySynchronizer` 하나만 쓴다. 그래서 이 열은
순수하게 "Redis 가 센 발급 수" 가 되고, `count_match` 는 다시
**"Redis 가 센 수 vs DB 에 실제로 들어간 행 수"** 의 교차 검증이 된다.
13.6 이후 의미가 없던 열인데, 되살아난 첫 측정에서 5,000 = 5,000 으로 통과했다.

### 16.6 쓰기 처리량 비교는 여기서 닫는다

병목 질문(16.4)이 닫혔고, 이보다 잘게 재려면 하네스를 바꿔야 하는데 그러면 13~16절과
단위가 달라져 지금까지의 기록과 비교가 깨진다. **그래서 여기서 닫는다.**

**닫는 시점의 상태를 그대로 남긴다.** `kafka-nocount` 의 쓰기 처리량은 **"≥160/s, 상한 미상"** 이다.
이것은 결함이 아니라 **자의 눈금이 여기까지**라는 뜻이다. 있는 도구로 억지 숫자를 만들면
그 숫자가 나중에 근거로 쓰인다. 모르는 것은 모른다고 적는다.

**다시 열어야 한다면** — 폴링을 잘게 쪼개지 말고 **행이 들어간 시각을 MySQL 이 직접 찍게 한다.**

```sql
ALTER TABLE issuance ADD COLUMN written_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

표본 추출 자체가 필요 없어져 부하 중이든 후든 전 구간 쓰기 곡선이 한 번의 조회로 나오고,
`issued_at` 과의 차가 곧 **접수 → 기록 지연 분포**다(이 프로젝트가 아직 못 본 값이다).
**컬럼을 앱이 아니라 하네스가 추가하는 것이 요령이다** — 엔티티를 안 건드리면 모든 태그를
다시 빌드할 필요가 없고, MySQL 의 `DEFAULT` 가 채우므로 **이전 태그도 `-NoBuild` 로 같은
잣대로 다시 잴 수 있다.** Hibernate 의 `ddl-auto: update` 는 모르는 컬럼을 지우지 않는다.

**다만 그 순간 13~16절의 "틱당" 값과는 직접 비교가 깨진다.** 되살리려면 이전 태그들을
같은 계측으로 다시 재야 한다.

**아직 답이 없는 질문 하나가 여기 남는다** — 응답 p99 가 왜 6.45 → 11.74ms 로 밀렸는지
(Hikari 풀? CPU?)는 안 갈랐다. 쓰기 곡선과 응답 분포를 겹쳐 봐야 알 수 있다.

## 17. 소비 실패에도 보상을 붙인다 — `kafka-dlt-restore` (2026-08-15)

> **§15 와 함께 4-4 에서 제거됐다 (2026-08-17).** DLT 이관은 그대로 남고
> 재고 복구만 빠졌다 — 사유는 §15 머리말과 [`architecture.md` §4](architecture.md).

15절은 **발행 실패**만 막았다. **소비 실패**는 그대로 열려 있었다.

`IssuanceWriter` 는 `DataIntegrityViolationException`(중복)만 삼키고 나머지는 밖으로 던진다.
그러면 `DefaultErrorHandler` 가 1초 × 3회 재시도하고 DLT 로 보낸다. 그 시점에

- Redis 재고는 **이미 깎여 있고 아무도 되돌리지 않는다** → 과소발급
- 그 사용자는 `coupon:{id}:users` 에 남아 **영영 재발급 불가**
- DB 안에는 아무 모순이 없어 `verify` 는 전부 OK 로 통과한다

**15절에서 프로듀서 쪽에 고친 것과 정확히 같은 결함이 컨슈머 쪽에 그대로 있었다.**
MySQL 이 잠깐 죽거나 커넥션이 마르면 바로 터진다.

### 17.1 먼저 발견한 것 — Kafka 자동설정이 아예 없었다

DLT 를 확인하려고 브로커를 들여다봤더니 **`issuance.requested.DLT` 토픽이 없었다.**
`KafkaTopicConfig` 가 `NewTopic` 빈으로 선언하고 있는데도 그렇다.

```
$ kafka-topics.sh --list
__consumer_offsets
issuance.requested          ← DLT 가 없다

앱 로그의 "AdminClientConfig values" : 0건   ← AdminClient 가 한 번도 안 떴다
spring-boot-autoconfigure-4.1.0.jar 안의 kafka 클래스 : 0개
runtimeClasspath : org.springframework.kafka:spring-kafka   ← starter 가 아니다
```

원인은 의존성이다. `build.gradle.kts` 가 `spring-boot-starter-kafka` 가 아니라
`org.springframework.kafka:spring-kafka` 를 직접 넣었는데, **Boot 4 부터 자동설정은 기술별
모듈(`spring-boot-kafka`)로 쪼개져 starter 로만 딸려온다.** 그래서 Kafka 자동설정이 통째로 없었다.

결과가 넷이다.

| | 실제 상태 |
|---|---|
| `KafkaAdmin` | 없다 → `KafkaTopicConfig` 는 **죽은 코드**였다 |
| `issuance.requested` | 앱이 아니라 **브로커 auto-create** 로 생겼다 |
| 파티션 3 | `KafkaTopicConfig.partitions(3)` 이 아니라 `docker-compose.yml` 의 `KAFKA_NUM_PARTITIONS: 3` 에서 왔다 |
| `application.yaml` 의 `spring.kafka.*` | `KafkaProperties` 바인딩이 없어 **거의 다 무시된다.** 지금 도는 건 `KafkaConfig` 가 `bootstrap-servers` 를 `@Value` 로 직접 읽어서다 |

**14.7 에 "`KafkaTopicConfig` 의 `partitions(3)` 이 병렬도의 상한" 이라고 적었던 것은 틀렸다.**
결과(파티션 3개)는 맞았지만 원인이 달랐다. 브로커 기본값이 바뀌면 조용히 따라 바뀐다.

그리고 네 번째가 제일 위험하다 — **설정을 yaml 에 적어 두고 먹었다고 믿는** 상태다.
이 프로젝트가 쿼리 로그·이미지 태그에서 반복해 당한 실패 모드와 같은 종류다.

`KafkaConfig` 가 팩토리를 전부 손으로 만들고 있으므로 같은 방식으로 `KafkaAdmin` 빈을
직접 추가해 살렸다. 의존성을 starter 로 바꾸면 자동설정이 통째로 딸려와 변수가 커진다.

### 17.2 무엇을 고쳤나

| 파일 | 고친 것 |
|---|---|
| `application/IssuanceCompensator.kt` (신설) | 보상 정책을 한 곳으로. `CouponService` 의 private `compensate` 를 여기로 옮겼다 |
| `KafkaErrorHandlerConfig` | 리커버러를 감쌌다 — **DLT 발행 → 그 다음 `restore`** |
| `KafkaConfig` | `KafkaAdmin` 빈 추가 (17.1) |

**보상을 한 클래스로 모은 이유.** 발행 실패와 소비 실패는 "Redis 는 깎였는데 그 발급이
성사되지 못했다" 는 **같은 상황**이다. 정책이 두 군데로 갈라지면 한쪽만 고치는 실수가 난다 —
실제로 15절에서 한쪽만 고쳤다.

**순서가 중요하다: 먼저 DLT 에 보존하고 그 다음에 되돌린다.** DLT 발행이 실패하면 거기서
예외가 나가 오프셋이 안 올라가고 재처리된다(유실보다 낫다). 반대 순서였다면
재고만 돌아오고 메시지는 사라지는 창이 생긴다.

**역직렬화 실패는 되돌릴 수 없다.** 값이 없으니 `couponId` 를 알 수 없다.
키는 `userId` 라 있지만 그것만으로는 부족하다. 조용히 넘어가면 재고가 샌 채 남으므로
ERROR 로 크게 남기고 넘어간다. 되돌리려면 `couponId` 를 헤더에 실어야 한다 — 아직 안 했다.

### 17.3 어떻게 확인하나 — `issuance` 테이블을 잠깐 치운다

소비 실패를 일으켜야 하는데, MySQL 을 통째로 세우면 `CouponService.issue` 의 `findById` 부터
막혀 요청이 컨슈머까지 가지도 못한다. **`issuance` 테이블만 잠깐 이름을 바꾼다** —
`coupon` SELECT 는 되고 `INSERT issuance` 만 실패한다. `ddl-auto: update` 는 기동 시에만
돌므로 중간에 테이블이 되살아나지 않는다.

이때 사용자는 **200 OK 를 받는다.** 발행은 성공했기 때문이다 — "200 은 발급 완료가 아니라
접수 완료" 라는 이 구조의 성격이 그대로 드러나는 자리다.

### 17.4 실측 (2026-08-15)

`kafka-dlt-restore`. `issuance` 테이블을 잠깐 치우고 발급 3건.

| 확인 | 기대 | 실측 |
|---|---|---|
| DLT 토픽 존재 | 있어야 한다 | `issuance.requested.DLT` ✓ (**직전까지는 없었다** — 17.1) |
| 발급 응답 | 200 (발행은 성공했다) | 200 × 3 |
| Redis 재고 | 5,000 (복구) | 5,000 |
| `coupon:1:users` | 0 | 0 |
| DLT 적재 | 3건 | `0:1 + 1:0 + 2:2` = 3 |
| 보상 로그 | 3줄 | 3줄 |
| 컨슈머 lag | 0 | 세 파티션 모두 0 |

```
15:58:45.109  [ntainer#0-0-C-1]  발급 기록(DLT 이관) 실패 — 재고 보상 완료: couponId=1, userId=1
15:58:45.109  [ntainer#0-2-C-1]  ... userId=2
15:58:48.653  [ntainer#0-2-C-1]  ... userId=3
```

15.2 와 같은 이유로 **"보상 완료"** 라는 문구가 판정을 가른다 — `restore.lua` 가 `1` 을
돌려줬다는 뜻이고, 재고가 깎여 있었고 되돌아왔다는 증거다. "애초에 안 깎였다" 와 구별된다.

**`lag 0` 도 같이 봐야 한다.** 실패한 3건의 오프셋이 커밋됐다는 뜻이라 다음 라운드에서
되살아나 오염시키지 않는다. 이것이 0 이 아니면 리셋 후 재소비가 일어난다.

### 17.5 재시도가 파티션을 세운다는 것이 실측으로 잡혔다

위 로그의 타임스탬프에 답이 있다. **userId 2 와 3 이 같은 스레드(`#0-2`)에서 3.5초 간격**으로
처리됐고, DLT 오프셋 분포(`0:1 / 1:0 / 2:2`)와 정확히 맞는다 — 파티션 2 에 두 건이 몰렸다.

Kafka 는 파티션 안에서 순서를 보장하므로 **두 번째 건은 첫 번째 건의 재시도 3초가 전부
끝날 때까지 시작조차 못 했다.** 14.7 에 추측으로 적어 둔 것이 여기서 확인됐다.

**실패 한 건이 그 파티션 뒤에 줄 선 정상 건들까지 3초씩 밀어낸다.**
부하 중에 DB 가 잠깐 흔들리면 처리량이 통째로 주저앉는다는 뜻이다. 지금 설정
(`FixedBackOff(1_000L, 3L)`)에서 한 건의 최악 지연은 약 3초이고, 그 뒤 대기열도 같이 밀린다.
줄이려면 재시도를 줄이거나 비블로킹 재시도(`@RetryableTopic` 계열)로 옮겨야 한다 — 아직 안 했다.
