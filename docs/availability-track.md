# 가용성(availability) 트랙 — Redis 대기실

2026-08-18 기록. 대상 이미지 `coupon-service:waiting-room`.

앞의 네 트랙이 "발급이 정확한가 / 얼마나 빠른가 / 얼마나 싸게 하는가 / 두 저장소가 맞는가" 를
봤다면, 이 트랙은 **감당 못 할 트래픽이 왔을 때 앱 앞에서 무엇을 하는가** 를 본다.
대기실은 발급 경로에 들어오는 인원 자체를 초당 N명으로 깎는다.

부하 조건이 다른 트랙과 다르므로 `docs/load-test-*.md` 의 절 번호 체계에 들어가지 않고
이 문서가 따로 있다 (정합성 트랙과 같은 취급).

러너는 `scripts/availability/windows/run.ps1` 이다. 원본(mac/bash)과 무엇이 다른지,
모드별 실행법은 [`scripts/availability/windows/README.md`](../scripts/availability/windows/README.md).

---

## 1. 측정 조건

| 항목 | 값 | 왜 |
|---|---|---|
| 진입 부하 | `constant-arrival-rate` 1,000/s × 20s | 통과 속도(100/s)보다 커야 줄이 쌓인다 |
| 재고 | 1,000,000 | 매진이 나면 재는 대상이 "대기실" 이 아니라 "매진 처리" 로 바뀐다 |
| 통과 속도 | 100/s (`COUPON_WAITING_ROOM_ADMIT_PER_SECOND`) | |
| 입장권 TTL | 30,000ms | duration 이 이보다 짧아야 앞쪽 입장권이 만료되지 않는다 |
| 허용 오차 | ±30% (70~130/s) | 드레인 틱 경계 때문. §3.1 |

**다른 트랙의 p99 와 나란히 놓고 비교하면 안 된다.** 조건이 다르다.

## 3. 분석

### 3.1 `2,100` 과 `2,000` 의 차이는 오차가 아니라 드레인 틱 1개다

둘 다 100 의 **정확한 배수**다 — `2100 = 21 × 100`, `2000 = 20 × 100`.

드레인은 `RedisWaitingRoom.drain` 의 `@Scheduled(fixedRate = 1000)` 이라 측정 창 20초와
무관하게 계속 돈다. k6 이 도는 20초 사이에 틱이 21번 들어가느냐 20번이냐가 갈릴 뿐이고,
통과 속도가 흔들린 것이 아니다.

배수로 딱 떨어진다는 것은 **매 틱 정확히 100명씩 나갔다**는 뜻이기도 하다.
줄에 항상 100명 이상 밀려 있어서 `waiting-room-drain.lua` 의 `ZRANGE 0, 99` 가 매번 가득 찼다.
(1,000/s 로 넣고 100/s 로 빼니 초당 900명씩 쌓인다.)

허용 오차 ±30% 를 둔 이유가 이 틱 경계다. **±1 틱 = ±100건 = ±5%p** 이므로 여유가 충분하다.

### 3.2 대기실이 발급 경로에서 걷어낸 양 — 20,001 → 2,000, 10분의 1

진입 요청 20,001건 중 발급까지 갈 수 있는 사람은 2,000명뿐이다. 나머지 18,001명은 줄에 남는다.
발급 API 가 보는 세상은 초당 100건짜리 워크로드고, 뒤에 얼마가 밀려 있든 그건 변하지 않는다.
이것이 이 트랙의 결론이다.

진입 자체는 싸다 — 1,000/s 에서 `http_req_duration` 평균 0.84ms, p95 0.97ms.
Redis `ZADD` + `ZRANK` 한 번이라 그렇다.

### 3.3 서버를 2배로 늘려도 100/s — 락이 실제로 걸려 있다는 증거

`waiting-room-drain.lua` 는 `ZRANGE` 와 `ZREM` 이 **한 스크립트 안에서** 일어난다.
락이 없었다면 두 인스턴스가 각각 다른 100명을 꺼내 갔을 것이고 결과는 **200/s** 였어야 한다.
100/s 가 나왔다는 것 자체가 `@SchedulerLock(name = "waiting-room-drain")` 이 물었다는 증거다.

Redis 에서 락 키도 확인했다:

```
job-lock:coupon:waiting-room-drain
```

(`RedisLockProvider(connectionFactory, "coupon")` — `infrastructure/scheduling/ShedLockConfig.kt`)

**`scale` 이 `single` 의 두 배로 나오면 락이 풀린 것이다.** 그때 볼 곳은 이 키다.

러너가 찍는 `VU 최대치` 는 다른 것을 본다 — *진입 트래픽*이 두 인스턴스로 갈렸는지다.
k6 시나리오가 `BASES[__VU % BASES.length]` 로 VU 단위 라운드로빈을 하므로 VU 가 1개면
전 요청이 한 대로만 간다. 다만 **전역 통과 속도 주장 자체는 그것과 독립**이다 —
2번 인스턴스가 떠서 드레인을 시도했다는 것만으로 성립한다 (줄은 어차피 Redis 한 곳이다).

### 3.4 `journey` 의 619건은 정확히 200 + 219 + 200 이다

진입 200 + 상태 폴링 219 + 발급 200. **사용자 1명당 요청이 1건에서 3.1건으로 늘었다.**
이것이 대기실의 비용이다 — 발급 API 가 받는 부하는 그대로 200건인데 전체 요청은 3배가 된다.

다만 늘어난 요청은 `waiting-room-status.lua` 의 `ZRANK` 한 방이라 발급보다 훨씬 싸다
(폴링 지연 평균 1.25ms). **비싼 요청을 싼 요청으로 바꾼 것**이지 요청을 없앤 것이 아니다.

### 3.5 폴링이 1.1회뿐인 것은 이 시나리오가 안 붐볐기 때문이다

200명 ÷ 100명/틱 = **2초면 전원 통과**다. 폴링 주기가 1초(+지터 0.25s)이니 1~2번이면 끝난다.
대기 시간 평균 1.29초 / p95 2.2초도 정확히 1틱·2틱 구조다.

그래서 이 조건에서는 **"폴링이 만드는 추가 요청량" 이라는 관전 포인트가 거의 안 드러난다.**
줄이 18,000명이면 꼬리 사용자는 180초를 기다리며 180번 폴링한다 — 거기서야 비용이 보인다.
원본(200명) 수치는 기준으로 두되, 붐비는 조건은 따로 재야 한다 (§5).

### 3.6 `http_req_duration` p90 111ms / p95 156ms 는 대기실이 느린 게 아니다

**이 트랙에서 응답시간을 읽으면 안 된다.** 두 가지가 섞여 있다.

첫째, 중앙값이 5.25ms 인 것이 힌트다. 619건 중 419건(진입 200 + 폴링 219)이 1~5ms 라
중앙값이 그 그룹에 떨어지고, **p90 부터가 발급 200건**이다.

둘째, 그 발급 지연의 정체는 대기실이 아니라 **`COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS=100`** 이다.
`CouponIssuePolicyReader.get` 이 캐시 미스 때 `Thread.sleep(100)` 을 하도록 효율 트랙이 넣어둔
값이고, `docker-compose.yml` 기본값이 100 이라 이 트랙에도 그대로 붙는다.
그래서 `run.ps1` 이 측정 머리에 이 값을 같이 찍는다 — 모르고 보면
"대기실을 붙였더니 p95 가 156ms" 라는 정반대 결론이 나온다.

셋째, 여기에 대기실 자체의 성질이 겹친다. **대기실은 발급을 평탄화하지 않고
1초 단위 버스트로 바꾼다.** 한 틱에 100명이 동시에 풀려 동시에 발급을 때리므로,
캐시 갱신 창마다 100건이 같은 로더를 기다린다. 초당 100건이라는 평균은 지켜지지만
그 100건은 1초에 고르게 퍼지지 않는다.

### 3.7 대조군은 기능이 **없는** 이미지를 요구한다 — baseline 을 잘못 재고 알아낸 것

`waiting-room` 이미지에서 `baseline` 을 돌렸더니 20,001건이 **전부 실패**했다
(`issue_failures = 20001`, `http_req_failed 100%`).

`baseline` 은 대기실을 붙이기 **전**을 재는 대조군인데, 이 이미지에는 `CouponController` 의
입장권 게이트가 들어 있다. `issue_flood.js` 는 매 요청 새 userId 를 쓰므로 입장권을 가진 사람이
하나도 없고, 전부 403 `NO_WAITING_ROOM_PASS` 로 튕겼다.

| 확인 | 값 | 뜻 |
|---|---|---|
| `issuance` 행 수 | 0 | 한 건도 발급되지 않았다 |
| `coupon:1:stock` | 1,000,000 | 재고 그대로. 발급 로직에 닿지도 않았다 |
| 응답 크기 | 330 bytes/건 | 발급 응답이 아니라 ProblemDetail 오류 본문 |
| `http_req_duration` p95 | 0.81ms | Redis `EXISTS` 한 번 하고 던진 속도. DB 를 안 탔다 |

**잰 것은 "대기실 없는 발급 처리량" 이 아니라 "게이트가 거절하는 속도" 였다.**
그런데 k6 은 정상 종료했고 러너는 `http_reqs = 20001` 을 결과처럼 찍었다 —
그대로 §3.2 의 대조군으로 썼으면 정반대 결론이 나온다.

지금은 러너가 막는다. 프로브의 기대 방향이 모드마다 반대다 —
`single`/`scale`/`journey` 는 대기실이 **있어야**, `baseline` 은 **없어야** 진행한다.
어긋나면 리셋 전에 멈추고 어느 태그로 띄우라는 안내를 낸다.

## 4. 읽는 순서와 의심할 곳

| 증상 | 먼저 볼 곳 |
|---|---|
| 입장권이 0건 | 드레인 스케줄러가 도는지. `docker compose logs coupon-service`, `waiting:room` 집합에 쿠폰이 들어갔는지 |
| `scale` 이 `single` 의 두 배 | 락이 풀렸다. `job-lock:coupon:waiting-room-drain` |
| 100 의 배수가 아닌 어중간한 값 | 줄이 마른 것(진입 rate < 통과 속도) 또는 입장권 TTL 만료. `Rate`/`Duration` 사전 조건을 러너가 막지만 값을 바꿔 돌렸다면 여기 |
| `scale` PASS 인데 VU 최대치 1 | 진입 트래픽이 한 대로만 갔다. 통과 속도 주장은 유효하지만 2대 분산은 확인 안 된 것 |
| p90/p95 가 100ms대 | §3.6. 캐시 시뮬레이션 지연이다. 이 트랙에서 응답시간을 읽지 않는다 |

판정은 **k6 이 아니라 Redis** 에서 나온다 — 통과 인원 = 살아 있는 입장권 키
(`waiting:{id}:pass<userId>`) 수. k6 이 아는 것은 "줄을 섰다" 까지다.

## 5. 남은 것

- **`baseline` 을 아직 안 쟀다.** 대기실 이미지로는 잴 수 없고(§3.7), 이미지를 되돌렸다 와야 한다:
  ```powershell
  .\build-and-run.ps1 -Tag reconcile-v3 -NoBuild     # 대기실 직전 이미지
  .\scripts\availability\windows\run.ps1 baseline
  .\build-and-run.ps1 -Tag waiting-room -NoBuild     # 되돌리기
  ```
  강의 흐름에서는 대기실을 만들기 **전에** 한 번 재고 넘어간다 — 우리는 그 시점을 지나쳐서
  뒤늦게 재는 상황이라 미뤄 두었다. §3.2 의 "10분의 1" 은 `single` 의
  진입 20,001 → 통과 2,000 만으로도 성립하므로 결론이 흔들리지는 않는다.
- **붐비는 조건의 `journey`.** `run.ps1 journey -Users 2000` 이면 꼬리가 20초를 기다려
  §3.5 의 폴링 비용이 실제로 드러난다. 원본(200명) 기록은 기준으로 남긴다.
- **`gateway` 모드(엣지 rate limit)는 아직 포팅하지 않았다** — `gateway/` 모듈도 compose 서비스도 없다.

## 6. 기록해 두는 관찰 — 방과 줄에 TTL 이 없다

`WaitingRoomRedisRepository` 가 만드는 키 중 TTL 이 붙는 것은 **입장권뿐**이다.

- `waiting:room` (활성 쿠폰 집합) — 방을 빼는 코드가 없다. 행사가 끝나도 남는다.
- `waiting:{id}:queue` (줄) — TTL 없음.

그래서 홍수가 끝난 뒤에도 드레인이 매초 죽은 방을 훑고, **이미 떠난 사용자에게 입장권을
계속 발급한다.** 이번 실행 기준 남은 18,001명 ÷ 100 = 약 180초 동안 그 일을 한다.
방이 여러 개 쌓이면 `activeRooms()` 가 매초 그 전부를 돈다.

측정에는 영향이 없다 — 하네스가 라운드마다 `FLUSHALL` 한다.
**지금은 코드를 건드리지 않는다.** 강의 진도에 맞춰 다룰 자리로 기록만 해 둔다.
