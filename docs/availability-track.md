# 가용성(availability) 트랙 — Redis 대기실

2026-08-18 기록. 대상 이미지는 절마다 다르다 —
`single`/`scale`/`journey` 는 `coupon-service:waiting-room`,
**`baseline` 은 대조군이라 대기실 직전의 `coupon-service:reconcile-v3`**(§3.7),
§7(게이트웨이)은 `coupon-service:gateway` + `coupon-gateway:latest` 다.

앞의 네 트랙이 "발급이 정확한가 / 얼마나 빠른가 / 얼마나 싸게 하는가 / 두 저장소가 맞는가" 를
봤다면, 이 트랙은 **감당 못 할 트래픽이 왔을 때 앱 앞에서 무엇을 하는가** 를 본다.
대기실은 발급 경로에 들어오는 인원 자체를 초당 N명으로 깎는다.

부하 조건이 다른 트랙과 다르므로 `docs/load-test-*.md` 의 절 번호 체계에 들어가지 않고
이 문서가 따로 있다 (정합성 트랙과 같은 취급).

러너는 `scripts/availability/windows/run.ps1` 이다. 원본(mac/bash)과 무엇이 다른지,
모드별 실행법은 [`scripts/availability/windows/README.md`](../scripts/availability/windows/README.md).

## 1. 측정 조건

| 항목 | 값 | 왜 |
|---|---|---|
| 진입 부하 | `constant-arrival-rate` 1,000/s × 20s | 통과 속도(100/s)보다 커야 줄이 쌓인다 |
| 재고 | 1,000,000 | 매진이 나면 재는 대상이 "대기실" 이 아니라 "매진 처리" 로 바뀐다 |
| 통과 속도 | 100/s (`COUPON_WAITING_ROOM_ADMIT_PER_SECOND`) | |
| 입장권 TTL | 30,000ms | duration 이 이보다 짧아야 앞쪽 입장권이 만료되지 않는다 |
| 허용 오차 | ±30% (70~130/s) | 드레인 틱 경계 때문. §3.1 |

**다른 트랙의 p99 와 나란히 놓고 비교하면 안 된다.** 조건이 다르다.

## 3. 분석

### 3.1 `2,100` 과 `2,000` 의 차이는 오차가 아니라 드레인 틱 1개다

둘 다 100 의 **정확한 배수**다 — `2100 = 21 × 100`, `2000 = 20 × 100`.

드레인은 `RedisWaitingRoom.drain` 의 `@Scheduled(fixedRate = 1000)` 이라 측정 창 20초와
무관하게 계속 돈다. k6 이 도는 20초 사이에 틱이 21번 들어가느냐 20번이냐가 갈릴 뿐이고,
통과 속도가 흔들린 것이 아니다.

배수로 딱 떨어진다는 것은 **매 틱 정확히 100명씩 나갔다**는 뜻이기도 하다.
줄에 항상 100명 이상 밀려 있어서 `waiting-room-drain.lua` 의 `ZRANGE 0, 99` 가 매번 가득 찼다.
(1,000/s 로 넣고 100/s 로 빼니 초당 900명씩 쌓인다.)

허용 오차 ±30% 를 둔 이유가 이 틱 경계다. **±1 틱 = ±100건 = ±5%p** 이므로 여유가 충분하다.

### 3.2 대기실이 발급 경로에서 걷어낸 양 — 20,000 → 2,100, 10분의 1

**대조군까지 갖춰졌다.** 같은 부하(1,000/s × 20s)를 같은 자리에 때린 두 결과다.

| | 발급 API 에 도달한 요청 |
|---|---|
| `baseline` (대기실 없음, `reconcile-v3`) | **20,000** |
| `single` (대기실 있음, `waiting-room`) | **2,100** (= 살아 있는 입장권 수) |

진입 요청 20,001건 중 발급까지 갈 수 있는 사람은 2,100명뿐이다. 나머지 18,001명은 줄에 남는다.
발급 API 가 보는 세상은 초당 100건짜리 워크로드고, 뒤에 얼마가 밀려 있든 그건 변하지 않는다.
**이것이 이 트랙의 결론이다** — 그리고 이제 "10분의 1" 이 한쪽 추정이 아니라 양쪽 실측이다.

진입 자체는 싸다 — 1,000/s 에서 `http_req_duration` 평균 0.84ms, p95 0.97ms.
Redis `ZADD` + `ZRANK` 한 번이라 그렇다.

### 3.3 서버를 2배로 늘려도 100/s — 락이 실제로 걸려 있다는 증거

`waiting-room-drain.lua` 는 `ZRANGE` 와 `ZREM` 이 **한 스크립트 안에서** 일어난다.
락이 없었다면 두 인스턴스가 각각 다른 100명을 꺼내 갔을 것이고 결과는 **200/s** 였어야 한다.
100/s 가 나왔다는 것 자체가 `@SchedulerLock(name = "waiting-room-drain")` 이 물었다는 증거다.

Redis 에서 락 키도 확인했다:

```
job-lock:coupon:waiting-room-drain
```

(`RedisLockProvider(connectionFactory, "coupon")` — `infrastructure/scheduling/ShedLockConfig.kt`)

**`scale` 이 `single` 의 두 배로 나오면 락이 풀린 것이다.** 그때 볼 곳은 이 키다.

러너가 찍는 `VU 최대치` 는 다른 것을 본다 — *진입 트래픽*이 두 인스턴스로 갈렸는지다.
k6 시나리오가 `BASES[__VU % BASES.length]` 로 VU 단위 라운드로빈을 하므로 VU 가 1개면
전 요청이 한 대로만 간다. 다만 **전역 통과 속도 주장 자체는 그것과 독립**이다 —
2번 인스턴스가 떠서 드레인을 시도했다는 것만으로 성립한다 (줄은 어차피 Redis 한 곳이다).

### 3.4 `journey` 의 요청 수는 정확히 진입 + 폴링 + 발급이다

| | 진입 | 폴링 | 발급 | 합계 | 1인당 |
|---|---|---|---|---|---|
| 200명 | 200 | 219 | 200 | **619** | 3.1건 |
| 2,000명 | 2,000 | 17,924 | 2,000 | **21,924** | **10.96건** |

두 조건 다 한 건도 안 새고 딱 맞는다. **이것이 대기실의 비용이다** —
발급 API 가 받는 부하는 사용자 수 그대로인데 전체 요청은 3배, 11배가 된다.

늘어난 요청 자체는 `waiting-room-status.lua` 의 `ZRANK` 한 방이라 발급보다 훨씬 싸다
(2,000명 조건에서 폴링 지연 med 592µs, p95 944µs — 발급의 100분의 1 수준).
**비싼 요청을 싼 요청으로 바꾼 것**이지 요청을 없앤 것이 아니다.

다만 **바뀐 비율이 사용자 수와 함께 나빠진다.** 200명일 때 폴링은 발급의 1.1배였는데
2,000명에서는 **9배**다. 이유는 §3.5.

### 3.5 폴링 총량은 사용자 수의 **제곱**에 비례한다 — 2,000명에서 확인

200명 조건에서는 이 비용이 안 보였다. 200 ÷ 100명/틱 = **2초면 전원 통과**라
폴링 주기(1초 + 지터 0.25초)로는 1~2번이면 끝난다 — 1인당 평균 1.095회, 사실상 **최소치에 눌려 있었다.**

2,000명으로 올리니 드러났다. 꼬리 사용자는 20초를 기다리며 **17번** 폴링한다.

**왜 제곱인가.** 사용자 `i` 는 `i/A` 초 기다리고(A = 통과 속도 100/s), 그동안 `(i/A)/T` 번 폴링한다
(T = 평균 폴링 주기 1.125초). 전부 더하면:

```
총 폴링 ≈ Σ(i/A)/T = N(N+1) / (2·A·T)     — N 에 대해 2차
```

| N | 예측 | 실측 | 오차 |
|---|---|---|---|
| 200 | 179 | 219 | +22.6% (최소 1회 바닥에 눌려 예측보다 많다) |
| 2,000 | **17,787** | **17,924** | **+0.8%** |

**사용자가 10배 늘었는데 폴링은 82배 늘었다.** 1인당 폴링도 예측 8.89회 / 실측 8.96회,
꼬리 사용자 예측 17.8회 / 실측 최대 17회로 맞는다.

이것이 폴링 방식의 성질이다 — **비용이 사용자 수가 아니라 "사용자 수 × 대기 시간" 에 붙는다.**
그리고 대기 시간 자체가 사용자 수에 비례하니 제곱이 된다.
통과 속도를 올리면 두 축이 동시에 줄어 폴링이 급격히 싸지고, 낮추면 급격히 비싸진다.

대기 시간 분포도 선형 드레인 그대로다 — 2,000 ÷ 100 = 20초 안에 균등하게 풀리므로
med 11.0s ≈ 절반, p95 19.9s ≈ 95%, max 21.2s ≈ 전체 + 폴링 발견 지연이다.

### 3.6 `http_req_duration` p90 111ms / p95 156ms 는 대기실이 느린 게 아니다

**이 트랙에서 응답시간을 읽으면 안 된다.** 두 가지가 섞여 있다.

첫째, 중앙값이 5.25ms 인 것이 힌트다. 619건 중 419건(진입 200 + 폴링 219)이 1~5ms 라
중앙값이 그 그룹에 떨어지고, **p90 부터가 발급 200건**이다.

둘째, 그 발급 지연의 정체는 대기실이 아니라 **`COUPON_CACHE_SIMULATED_LOAD_LATENCY_MS=100`** 이다.
`CouponIssuePolicyReader.get` 이 캐시 미스 때 `Thread.sleep(100)` 을 하도록 효율 트랙이 넣어둔
값이고, `docker-compose.yml` 기본값이 100 이라 이 트랙에도 그대로 붙는다.
그래서 `run.ps1` 이 측정 머리에 이 값을 같이 찍는다 — 모르고 보면
"대기실을 붙였더니 p95 가 156ms" 라는 정반대 결론이 나온다.

셋째, 여기에 대기실 자체의 성질이 겹친다. **대기실은 발급을 평탄화하지 않고
1초 단위 버스트로 바꾼다.** 한 틱에 100명이 동시에 풀려 동시에 발급을 때리므로,
캐시 갱신 창마다 100건이 같은 로더를 기다린다. 초당 100건이라는 평균은 지켜지지만
그 100건은 1초에 고르게 퍼지지 않는다.

**2,000명 조건이 이 구조를 더 선명하게 보여준다.** 21,924건 중 발급이 2,000건 = **9.1%** 이므로
**p90.9 부터가 발급**인데, 실측이 정확히 그렇다 — p90 은 아직 폴링 구간(4.51ms)이고
p95 에서 발급 구간(98.9ms)으로 넘어간다. med 는 622µs 로 폴링 값이다.
max 가 238ms(200명) → **872ms**(2,000명)로 나빠진 것은 틱이 2번에서 20번으로 늘어
가장 나쁜 버스트를 만날 기회가 그만큼 많아졌기 때문이다.

**즉 이 수치들은 대기실의 응답시간이 아니다.** 셋 중 어느 것도 이 트랙이 재려는 값이 아니다.

### 3.7 대조군은 기능이 **없는** 이미지를 요구한다 — baseline 을 잘못 재고 알아낸 것

`waiting-room` 이미지에서 `baseline` 을 돌렸더니 20,001건이 **전부 실패**했다
(`issue_failures = 20001`, `http_req_failed 100%`).

`baseline` 은 대기실을 붙이기 **전**을 재는 대조군인데, 이 이미지에는 `CouponController` 의
입장권 게이트가 들어 있다. `issue_flood.js` 는 매 요청 새 userId 를 쓰므로 입장권을 가진 사람이
하나도 없고, 전부 403 `NO_WAITING_ROOM_PASS` 로 튕겼다.

| 확인 | 값 | 뜻 |
|---|---|---|
| `issuance` 행 수 | 0 | 한 건도 발급되지 않았다 |
| `coupon:1:stock` | 1,000,000 | 재고 그대로. 발급 로직에 닿지도 않았다 |
| 응답 크기 | 330 bytes/건 | 발급 응답이 아니라 ProblemDetail 오류 본문 |
| `http_req_duration` p95 | 0.81ms | Redis `EXISTS` 한 번 하고 던진 속도. DB 를 안 탔다 |

**잰 것은 "대기실 없는 발급 처리량" 이 아니라 "게이트가 거절하는 속도" 였다.**
그런데 k6 은 정상 종료했고 러너는 `http_reqs = 20001` 을 결과처럼 찍었다 —
그대로 §3.2 의 대조군으로 썼으면 정반대 결론이 나온다.

지금은 러너가 막는다. 프로브의 기대 방향이 모드마다 반대다 —
`single`/`scale`/`journey` 는 대기실이 **있어야**, `baseline` 은 **없어야** 진행한다.
어긋나면 리셋 전에 멈추고 어느 태그로 띄우라는 안내를 낸다.

제대로 잰 것은 이미지를 되돌려서다. 다시 잴 일이 있으면:

```powershell
# 돌아올 태그를 먼저 적어 둔다 (.env 의 COUPON_IMAGE_TAG, 또는 러너가 찍는 "측정 대상 이미지")
.uild-and-run.ps1 -Tag reconcile-v3 -NoBuild     # 대기실 직전 이미지
.\scriptsvailability\windows
un.ps1 baseline
.uild-and-run.ps1 -Tag <적어 둔 태그> -NoBuild    # 되돌리기
```

**브랜치 전환으로는 대신할 수 없다.** `reconcile` 브랜치에 대기실 소스가 없는 것은 맞지만,
재는 대상은 워킹트리가 아니라 떠 있는 컨테이너라 `git checkout` 은 그것을 안 바꾼다.
게다가 이 트랙의 하네스가 통째로 대기실 커밋에서 들어왔다 — 이전 브랜치로 가면
`run.ps1` 부터 없어서 돌릴 것이 없다. 태그로 나누는 이유가 이것이다.

### 3.8 대조군이 멀쩡했다는 것 — 대기실을 정당화하는 숫자는 여기 없다

`baseline` 은 20,000건을 **전부** 처리했다. 실패 0, p95 1.7ms, k6 이 쓴 VU 는 최대 2개다.
1,000개를 예약해 뒀는데 2개로 1,000/s 를 채웠다는 것은 요청 하나가 1ms 언저리에 끝났다는 뜻이다.

즉 **이 조건에서 발급 API 는 대기실 없이도 아무 문제가 없었다.**
재고가 100만이라 매진 경합이 없고, 1,000/s 는 이 앱의 한계 근처가 아니다.

그래서 정직하게 적어 둔다 — 이 트랙이 증명한 것은 **"대기실이 발급 경로 인원을 10분의 1로 깎는다"**
는 사실이지, "대기실이 없으면 앱이 죽는다" 가 아니다. 후자를 보이려면 재고를 실제 경품 수량으로
낮추거나(매진 경합) 부하를 앱 한계까지 올려야 하고, 그러면 §1 의 조건이 바뀌어
지금 기록과 나란히 못 놓는다.

같은 이유로 §7 의 게이트웨이가 별도로 필요하다. 대기실은 **인원**을 깎지만
한 사람이 2,000번 때리는 것은 못 막는다 — 그건 앞단에서 끊어야 한다.

---

## 4. 읽는 순서와 의심할 곳

| 증상 | 먼저 볼 곳 |
|---|---|
| 입장권이 0건 | 드레인 스케줄러가 도는지. `docker compose logs coupon-service`, `waiting:room` 집합에 쿠폰이 들어갔는지 |
| `scale` 이 `single` 의 두 배 | 락이 풀렸다. `job-lock:coupon:waiting-room-drain` |
| 100 의 배수가 아닌 어중간한 값 | 줄이 마른 것(진입 rate < 통과 속도) 또는 입장권 TTL 만료. `Rate`/`Duration` 사전 조건을 러너가 막지만 값을 바꿔 돌렸다면 여기 |
| `scale` PASS 인데 VU 최대치 1 | 진입 트래픽이 한 대로만 갔다. 통과 속도 주장은 유효하지만 2대 분산은 확인 안 된 것 |
| p90/p95 가 100ms대 | §3.6. 캐시 시뮬레이션 지연이다. 이 트랙에서 응답시간을 읽지 않는다 |

판정은 **k6 이 아니라 Redis** 에서 나온다 — 통과 인원 = 살아 있는 입장권 키
(`waiting:{id}:pass<userId>`) 수. k6 이 아는 것은 "줄을 섰다" 까지다.

---

## 5. 남은 것

다섯 모드(`baseline`/`single`/`scale`/`journey`/`gateway`)와 붐비는 조건의 `journey` 까지 다 쟀다.
지금 남은 것은 하네스의 한계 하나다.

- **`journey` 는 2,800명 근처가 천장이다.** `run.ps1` 이 `MAX_WAIT_SECONDS = 30` 을 상수로 넘기고
  파라미터가 없다. 대기 시간이 `N/100 + 폴링 발견 지연(~1.25초)` 이므로
  `N ≈ (30 - 1.25) × 100 = 2,875` 를 넘기면 꼬리가 `통과 대기시간 초과` 로 실패한다.
  2,000명 실측 max 가 21.2초였으니 여유는 9초뿐이다.
  더 붐비는 조건을 재려면 이 값을 파라미터로 빼야 한다 — **입장권 TTL(30초)도 같이 봐야 한다.**
  둘이 같은 30초라 TTL 을 안 올리고 대기만 늘리면 앞쪽 입장권이 만료된다.

---

## 6. 기록해 두는 관찰 — 방과 줄에 TTL 이 없다

`WaitingRoomRedisRepository` 가 만드는 키 중 TTL 이 붙는 것은 **입장권뿐**이다.

- `waiting:room` (활성 쿠폰 집합) — 방을 빼는 코드가 없다. 행사가 끝나도 남는다.
- `waiting:{id}:queue` (줄) — TTL 없음.

그래서 홍수가 끝난 뒤에도 드레인이 매초 죽은 방을 훑고, **이미 떠난 사용자에게 입장권을
계속 발급한다.** 이번 실행 기준 남은 18,001명 ÷ 100 = 약 180초 동안 그 일을 한다.
방이 여러 개 쌓이면 `activeRooms()` 가 매초 그 전부를 돈다.

측정에는 영향이 없다 — 하네스가 라운드마다 `FLUSHALL` 한다.
**지금은 코드를 건드리지 않는다.** 강의 진도에 맞춰 다룰 자리로 기록만 해 둔다.

## 7. 게이트웨이 엣지 rate limit — 어뷰저를 앱 앞에서 컷

대기실은 **모두를 줄 세워** 발급 경로의 인원을 초당 N명으로 깎는다.
그런데 §3 의 어느 숫자도 "한 사람이 초당 수백 번 때리는" 상황을 안 본다.
`journey` 는 정상 사용자 200명의 여정만 재고, `single`/`scale` 은 진입 요청을 사람 구분 없이 센다.
어뷰저는 대기실 입장에서 **정상 사용자와 구별되지 않는다** — 줄에 2,001번 서는 사람일 뿐이다.

게이트웨이는 그 앞단이다. 사용자별 토큰 버킷으로 **앱에 닿기 전에** 끊는다.

### 7.1 측정 조건 (다른 절과 다르다)

| 항목 | 값 | 다른 절 |
|---|---|---|
| 어뷰저 | 1명(`X-User-Id: 424242`)이 **200 req/s** | — |
| 정상 사용자 | 매 요청 다른 id 로 **20 req/s** | — |
| 시간 | **10초** | 20초 |
| 허용 오차 | **±20%** | ±30% |
| 토큰 버킷 | `replenish 5/s`, `burst 10` | — |
| 접속 | 게이트웨이 `8090` (컨테이너 안에서는 `gateway:8080`) | 앱 `8080` 직접 |

**§1 의 조건과 나란히 놓고 읽으면 안 된다.** 러너의 파라미터도 `-AbuserRate` /
`-GatewayDuration` / `-GatewayTolerancePercent` 로 분리해 두었다 — 한쪽을 만졌을 때
다른 쪽 기준값이 조용히 따라 움직이지 않게 하려는 것이다.

```powershell
.\gradlew.bat :gateway:jibBuildTar          # jibDockerBuild 는 교착 (CLAUDE.md)
docker load -i gateway\build\jib-image.tar
.\scripts\availability\windows\run.ps1 gateway
```

### 7.2 결과 — PASS

2026-08-18. 앱 `coupon-service:gateway`, 게이트웨이 `coupon-gateway:latest`.

| 지표 | 기대 | 실측 | |
|---|---|---|---|
| 어뷰저 통과 | `burst + replenish×초` = **60** (허용 48~72) | **65** | PASS |
| 어뷰저 차단(429) | 발사한 나머지 | **1,936** / 2,001 | |
| 어뷰저 실패(그 외) | 0 | **0** | PASS |
| 정상 통과 | **200** (20/s × 10s) | **201** / 201 | PASS |
| 정상 차단 | **0** — 각자 버킷이라 안 막혀야 한다 | **0** | PASS |
| `dropped_iterations` | 0 | **0** | PASS |

**어뷰저 1명이 2,001번을 때려서 앱에 닿은 것은 65번이다.** 96.8% 가 앱 앞에서 끝났다.
같은 시간에 정상 사용자 201명은 한 명도 안 막혔다 — 이것이 대기실만으로는 안 되는 부분이다.
대기실 입장에서 어뷰저는 "줄에 2,001번 선 사람" 일 뿐이라 §3 의 어떤 지표로도 구별되지 않는다.

응답시간(참고용, 이 트랙이 재는 값은 아니다):

| | med | p90 | p95 | max |
|---|---|---|---|---|
| 전체 2,202건 | 0.85ms | 3.02ms | 3.76ms | 20.03ms |
| 200 응답만 (266건) | 3.56ms | 4.73ms | 5.38ms | 10.02ms |

### 7.3 `65` 는 `60` 의 오차가 아니라 초 단위 절삭 1칸이다

`65 = 10 + 5 × 11`. 기대치 `60 = 10 + 5 × 10` 과의 차이는 정확히 **채움 1회분**이다.
§3.1 에서 `2,100` 과 `2,000` 이 드레인 틱 1개 차이였던 것과 같은 종류다.

원인은 Spring Cloud Gateway 의 Lua 스크립트에 있다
(`META-INF/scripts/request_rate_limiter.lua`, spring-cloud-gateway-server-webflux 5.0.2):

```lua
local now = tonumber(ARGV[3]) or redis.call('TIME')[1]
local delta = math.max(0, now-last_refreshed)
local filled_tokens = math.min(capacity, last_tokens+(delta*rate))
```

`RedisRateLimiter` 는 `ARGV[3]` 에 **빈 문자열**을 넘긴다(`RedisRateLimiter.java:265`).
`tonumber("")` 는 `nil` 이므로 `redis.call('TIME')[1]` 로 떨어지는데, 이것은 **정수 초**다.
즉 채움이 밀리초로 연속하지 않고 **초 경계에서 5개씩 뚝뚝** 들어간다.
10초짜리 실행이 정수 초 경계를 11번 지나면 55개가 채워진다.

**그래서 이 측정에 ±20% 오차를 두는 것이다.** ±1 경계 = ±5건 = ±8%p 이므로 여유가 있다.
실행 시각이 초 경계에 어디에 걸리느냐에 따라 60 또는 65 가 나온다 — 구현이 흔들린 것이 아니다.

같은 스크립트에서 버킷 키의 TTL 도 보인다 — `math.floor(capacity/rate * 2)` = **4초**.
마지막 요청 4초 뒤면 버킷이 사라지므로, 라운드를 연달아 돌려도 앞 실행의 토큰이 안 넘어온다.

### 7.4 `http_req_failed 87.92%` 는 이 절에서만 정상이다

```
http_req_failed: 87.92%  1936 out of 2202
```

**다른 트랙이었으면 여기서 읽기를 멈춰야 하는 숫자다** (CLAUDE.md: `checks` 가 100% 가 아니면
나머지 숫자는 읽지 않는다). 여기서는 반대다 — 그 1,936건이 **재려고 만든 429** 다.
k6 은 4xx 를 `expected_response:false` 로 세므로 컷이 잘 될수록 이 비율이 올라간다.

판정을 `http_req_failed` 가 아니라 `abuser_*` / `normal_*` 카운터로 하는 이유가 이것이다.
러너도 종료 코드나 이 비율이 아니라 요약 JSON 의 여섯 카운터를 본다.

### 7.5 컷은 0.85ms, 통과는 3.56ms — 싸게 끊는다는 것의 의미

전체 중앙값 0.85ms 는 **429 를 돌려준 속도**다 (2,202건 중 1,936건이 429라 중앙값이 그쪽에 떨어진다).
앱까지 간 200 응답만 보면 중앙값 3.56ms 다.

거절이 통과의 1/4 값이라는 것이 요점이다. 어뷰저를 앱에서 막으려면 최소한
Redis 조회 + 애플리케이션 스레드가 필요한데, 게이트웨이는 Redis `EVALSHA` 한 번으로 끝낸다.
**어뷰저 트래픽이 늘어도 비싼 쪽(앱)의 부하는 상수로 유지된다.**

§3.2 의 진입 지연(평균 0.84ms)과 나란히 놓지는 말 것 — 그쪽은 1,000/s 조건이고
게이트웨이를 안 거친 값이다.

### 7.6 밟은 함정 — 라우트 경로가 안 맞아도 초록색이 나온다

강의 원본의 predicate 는 `/api/coupons/*/issue`, `/api/issuances/*/use`,
`/api/users/me/issuances` 다. **이 저장소는 셋 다 `/api/v1/` 이 붙는다.**
대기실(`/api/waiting-room/**`)만 원본과 같다.

그대로 두면 발급·사용·조회가 게이트웨이를 아예 안 거친다(404). 즉 rate limit 이
정작 지켜야 할 발급 경로를 안 지키는 상태다. 그런데 **k6 시나리오가 때리는 것은
`/api/waiting-room` 뿐이라 어뷰저 컷은 정상으로 보이고 PASS 가 찍힌다.**
`baseline` 을 대기실 이미지로 쟀을 때(§3.7)와 같은 종류의 실패다 —
에러로 죽지 않고 그럴듯한 숫자가 나온다.

러너는 측정에 들어가기 전에 `GET /api/v1/users/me/issuances` 를 8090 으로 찔러
200 이 아니면 멈춘다. 404 는 "옛 라우트가 든 이미지" 로 따로 구분해 안내한다.

### 7.7 읽는 순서

1. `dropped_iterations` — 0 이 아니면 부하가 예정대로 안 나간 것이라 나머지를 읽지 않는다.
2. 실패(200/429 외) — 있으면 한도 문제가 아니라 게이트웨이 뒤나 라우트가 깨진 것이다.
3. `정상 차단` — 0 이 아니면 버킷이 사용자별이 아니다. `userIdKeyResolver` 를 의심한다.
4. `어뷰저 차단` — 0 이면 라우트에 `RequestRateLimiter` 가 안 붙었다.
5. `어뷰저 통과` — 허용 구간을 벗어나면 그때가 한도 값 자체를 보는 순간이다.
